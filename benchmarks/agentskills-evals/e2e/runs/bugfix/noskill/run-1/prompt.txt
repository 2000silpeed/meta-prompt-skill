결제 모듈에서 금액의 소수점 반올림이 가끔 틀리게 계산되는 버그가 있습니다. 근본 원인을 찾아서 고쳐 주세요. 결제 금액은 1원, 1센트만 틀려도 정산 불일치나 고객 클레임으로 이어지기 때문에, 이번 작업에서는 증상이 사라지는 것보다 원인을 정확히 이해하고 고치는 것이 중요합니다.

## 알고 있는 정보
- 결제 모듈 위치: [예: src/payments/ — 모르면 비워 두세요. 직접 찾아 주세요]
- 틀린 사례: [예: 10.005 → 10.01이어야 하는데 10.00이 나옴 / 주문 ID, 로그 등. 없으면 비워 두세요]
- 의도한 반올림 정책: [예: 통화별 최소 단위로 HALF_UP, 세금은 항목별 계산 후 합산 등. 모르면 비워 두세요]

"가끔"만 틀린다는 점이 단서입니다. 특정 입력값에서만 재현될 가능성이 높습니다.

## 진행 방식
1. 먼저 코드베이스에서 금액을 계산·변환·반올림하는 경로를 모두 파악하세요. 가격, 할인, 세금, 수수료, 분할 결제, 환불, 통화 변환, 직렬화/역직렬화(JSON, DB 컬럼 타입), 외부 PG 연동부를 포함합니다.
2. 수정하기 전에 버그를 재현하는 실패 테스트를 작성하세요. 재현이 안 되면 추측으로 고치지 말고, 어떤 가설들을 확인했는지 정리해서 보고하세요.
3. 자주 나오는 원인들입니다. 이 목록에 갇히지 말고 실제 코드에서 근거를 확인하세요.
   - 부동소수점(float/double)으로 금액을 다룸 (예: 1.005가 실제로는 1.00499…로 저장됨)
   - 경로마다 반올림 방식이 다름 (HALF_UP vs HALF_EVEN, 언어 기본 round의 동작 차이)
   - 반올림 시점이 다름 (항목별로 반올림 후 합산 vs 합산 후 반올림, 중간 단계에서 반복 반올림)
   - 통화별 소수 자릿수를 무시함 (KRW·JPY 0자리, USD 2자리, BHD·KWD 3자리)
   - 분할·안분 시 나머지 처리가 없어 합계가 원금과 맞지 않음
   - 문자열이나 DB 타입으로 변환하면서 정밀도가 손실됨
4. 원인을 고친 뒤에는 같은 패턴이 다른 경로에도 있는지 확인하세요. 같은 원인이면 함께 고치고, 범위 밖이라고 판단되면 위치만 보고하세요.
5. 경계값 테스트를 추가하세요. x.xx5 같은 반올림 경계, 0, 음수(환불), 아주 큰 금액, 통화별 자릿수, 분할 합계가 원금과 같은지 등을 포함합니다. 마지막으로 기존 테스트 전체를 실행하세요.

## 지켜야 할 것
- 의도된 반올림 정책을 함부로 바꾸지 마세요. 정책 자체가 불명확하거나, 코드 곳곳이 서로 다른 정책을 쓰고 있어서 하나를 골라야 하는 상황이라면 임의로 정하지 말고 선택지와 각각의 영향을 정리해 보고하세요. 회계·정산 기준과 연결된 결정입니다.
- 수정 범위는 버그 원인에 맞추세요. 금액 타입을 전면 교체하는 식의 대규모 리팩터링이 필요하다고 판단되면, 하지 말고 제안으로 남기세요.
- DB 스키마 변경, 마이그레이션, 기존 결제 데이터 수정, 외부 PG API 호출 방식 변경은 하지 말고 필요성만 보고하세요.
- 테스트를 통과시키려고 기대값을 바꾸거나 테스트를 건너뛰지 마세요. 기존 테스트의 기대값 자체가 틀렸다고 판단되면 근거와 함께 따로 표시하세요.
