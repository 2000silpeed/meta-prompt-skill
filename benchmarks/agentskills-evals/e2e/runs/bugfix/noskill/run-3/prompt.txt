결제 모듈에서 금액의 소수점 반올림 결과가 가끔 틀리는 버그를 찾아서 고쳐 줘. 항상 틀리는 게 아니라 특정 금액이나 특정 경로에서만 틀린다. 이런 증상은 대개 금액을 부동소수점(float/double)으로 다루거나, 반올림 방식이 코드 곳곳에서 서로 다르거나, 반올림하는 시점이 계산 순서상 잘못된 경우에 생긴다. 다만 이건 추정일 뿐이니 코드를 보고 실제 원인을 확인해 줘.

[알고 있는 정보: 아래 항목 중 아는 것만 채우고 나머지는 지울 것]
- 결제 모듈 위치: <경로>
- 재현된 사례: <예: 입력 금액 / 기대값 / 실제값>
- 회사 반올림 정책: <예: 원 단위 절사, 센트 단위 HALF_UP, 은행가 반올림(HALF_EVEN) 등>
- 다루는 통화: <예: KRW만 / USD·JPY 등 다중 통화>

진행 순서:

1. 조사부터 한다. 금액이 들어오는 곳(API 입력, DB 로드, 외부 PG 응답)부터 저장되거나 PG로 나가는 곳까지 흐름을 따라가면서 다음을 확인해 줘.
   - 금액을 담는 타입. float/double인지, Decimal·BigDecimal·정수(최소 화폐 단위) 같은 정밀 타입인지.
   - 반올림이 일어나는 모든 위치와 각각 쓰는 방식. round(), Math.round, toFixed, 포맷팅 함수, DB 컬럼의 scale, 직렬화 과정에서 일어나는 암묵적 반올림까지 포함.
   - 반올림 시점. 할인, 세금, 수수료, 분할결제, 환율 계산 중간에 반올림하는지 마지막에 한 번만 하는지. 항목별로 반올림한 값의 합과 합계를 반올림한 값이 어긋나는 곳이 있는지.
   - 정밀 타입으로 바꾸는 과정에서 float를 거치는 곳. 예를 들어 Decimal(0.1)이나 new BigDecimal(double)처럼 생성하는 코드.
   - 통화별 소수 자릿수 처리. KRW·JPY는 0자리, USD는 2자리처럼 다른데 하드코딩되어 있는지.

2. 고치기 전에 버그를 재현하는 실패 테스트를 먼저 쓴다. 재현 사례가 위에 주어졌다면 그걸 쓰고, 없으면 조사 결과로 문제를 일으키는 입력을 직접 찾아서 써 줘. 경계값(정확히 .5인 값, 1.005나 2.675처럼 이진 표현이 부정확한 값, 음수와 환불, 0, 아주 큰 금액)도 테스트에 넣어 줘.

3. 근본 원인을 고친다. 특정 입력만 보정하는 땜질은 하지 말아 줘. 반올림 로직이 여러 곳에 흩어져 있으면 하나의 함수나 유틸로 모아서 반올림 방식과 자릿수를 명시적으로 지정하게 해 줘. 반올림 정책이 위에 주어졌다면 그대로 따르고, 주어지지 않았다면 기존 코드에서 가장 많이 쓰이는 방식을 따르되 그렇게 판단한 근거를 보고에 남겨 줘.

4. 바뀌는 범위는 이 버그를 고치는 데 필요한 만큼으로 한정한다. 다만 다음 변경은 기존 데이터나 외부 연동에 영향을 줄 수 있으니 직접 하지 말고 필요성과 이유만 보고해 줘: DB 스키마나 컬럼 타입 변경, 외부 API 응답 형식 변경, 이미 저장된 금액 데이터의 마이그레이션.

5. 새로 쓴 테스트와 기존 테스트 스위트를 모두 돌려서 통과하는지 확인한다. 실패하는 테스트가 있으면 숨기지 말고 출력과 함께 보고해 줘.

끝나면 다음을 정리해서 보고해 줘.
- 근본 원인. 어느 파일의 몇 번째 줄에서 무엇이 왜 틀렸는지.
- 수정한 내용과 그렇게 고친 이유.
- 추가한 테스트와 전체 테스트 실행 결과.
- 같은 원인으로 이미 잘못 처리되었을 수 있는 과거 거래의 유형과 범위(추정이면 추정이라고 밝힐 것), 그리고 손대지 않았지만 따로 처리가 필요한 사항.
