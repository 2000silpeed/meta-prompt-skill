금액 반올림 버그를 고쳤습니다. 테스트 9개가 모두 통과합니다(기존 3개 + 새로 추가한 회귀 테스트 6개). 커밋은 하지 않았고, 변경 파일은 `payment/money.py`, `payment/cart.py`, `tests/test_money.py`입니다.

## 원인
`payment/money.py`의 `round_amount`가 `round(float(value), 2)`로 되어 있어서, `docs/PAYMENT_POLICY.md`의 규칙과 세 군데에서 어긋났습니다.

| 문제 | 예시 (수정 전 → 정책상 정답) |
|---|---|
| 파이썬 `round()`가 은행가 반올림이라 0.5가 짝수 쪽으로 감 | `0.125 → 0.12` (정답 0.13) |
| float 오차로 2.675가 실제로는 2.67499…로 저장됨 | `2.675 → 2.67` (정답 2.68) |
| 통화를 무시하고 항상 소수 2자리로 반올림 | KRW `1234.5 → 1234.5` (정답 1235) |

"가끔" 틀렸던 건 끝자리가 정확히 5인 금액이나 원·엔 금액에서만 오차가 났기 때문입니다.

그리고 `split_amount`(분할 결제)도 고쳤습니다. 나눈 금액의 합이 원래 금액과 맞지 않았습니다(예: `10.00`을 3으로 나누면 `[3.33, 3.33, 3.33]`이라 합이 9.99).

## 수정 내용
- **`payment/money.py`**
  - 반올림을 `Decimal`과 `ROUND_HALF_UP`(사사오입)으로 바꿨습니다. float는 `str()`을 거쳐 변환해 저장 오차를 피합니다.
  - 통화별 소수 자릿수(`CURRENCY_DECIMALS`)를 적용합니다. 등록되지 않은 통화는 `ValueError`를 냅니다.
  - `split_amount`는 금액을 최소 단위로 나누고, 나머지를 앞 순번부터 1단위씩 더합니다. 예: `[3.34, 3.33, 3.33]`.
- **`payment/cart.py`**: 줄 금액, 할인, 세금 계산과 합계 누적을 `Decimal`로 처리합니다. 계산 순서(할인 다음 세금, 각각 반올림)는 그대로 둡니다.
- 반환 타입은 기존처럼 `float`로 유지해서, 이 함수를 쓰는 다른 코드에는 영향이 없습니다.

## 테스트
- 수정 전 코드로 위 표의 오류들을 직접 재현했고, 수정 후에는 모두 정답이 나옵니다.
- 추가한 테스트가 다루는 경우: 0.5 사사오입, float 표현 오차, 통화별 자릿수, 분할 결제 합계 일치, 장바구니 할인·세금 반올림, 환불 금액.
- 처음 작성한 KRW 장바구니 테스트의 기대값(995)은 제 계산 실수였습니다. 정책대로 다시 계산하면 1005 − 101 + 90 = 994라서 기대값을 994로 고쳤습니다. 코드는 바꾸지 않았습니다.
- 실제 결제가 일어나는 `payment/gateway.py`는 건드리거나 호출하지 않았습니다.

## 확인이 필요한 점
- 반올림 결과가 바뀐 만큼, 이 함수를 쓰는 곳의 금액도 1단위(0.01달러나 1원) 달라질 수 있습니다. 정책에 맞는 쪽으로 바뀌는 것이지만, 기존 주문이나 정산 데이터와 맞춰 볼 때는 이 점을 감안해야 합니다.
- 음수 금액은 0에서 먼 쪽으로 반올림하고(`-0.125 → -0.13`), 분할할 때도 같은 부호로 나눕니다.
