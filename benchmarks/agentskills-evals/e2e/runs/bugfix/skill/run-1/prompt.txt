## 진행 순서
1. 금액이 입력되고, 계산되고(할인·세금·수수료·환율·분할), 반올림되고, 저장·직렬화되고, 외부로 전송되는 경로를 끝까지 추적하세요. 반올림이나 형 변환이 일어나는 모든 지점을 목록으로 만드세요.
2. 고치기 전에 버그를 재현하는 실패 테스트를 먼저 작성하세요. 증상 예시가 없으면 아래 함정 목록에서 의심되는 경계값으로 재현을 시도하세요. 재현에 실패하면 시도한 입력을 기록하세요.
3. 원인을 한 문장으로 특정한 뒤 최소 범위로 수정하세요. 같은 원인을 가진 다른 위치가 있으면 함께 고치고, 위치마다 그렇게 판단한 근거를 남기세요.
4. 새 테스트와 기존 테스트 전체를 실행해서 통과를 확인하세요.

## 이 영역에서 놓치기 쉬운 함정
- 부동소수 연산: float/double로 계산하면 0.1 + 0.2, 1.005 × 100 같은 값이 미세하게 어긋나서 반올림 경계에서 결과가 뒤집힙니다. "가끔 틀린다"는 증상의 가장 흔한 원인입니다.
- decimal 변환 시점: Decimal(1.005)처럼 float에서 바로 만들면 이미 오차가 섞인 값이 들어갑니다. 문자열이나 정수(최소 단위)에서 생성해야 합니다. JSON 파싱, DB 드라이버, ORM이 중간에 금액을 float로 바꾸는 지점도 확인하세요.
- 반올림 모드 불일치: 언어나 라이브러리의 기본값은 HALF_EVEN(은행가 반올림)인 경우가 많습니다. 예: Python round(), Java BigDecimal 일부 경로. JS의 toFixed는 부동소수 표현 때문에 결과가 일정하지 않습니다. 모듈 안에서 반올림 모드가 섞여 있지 않은지 보세요.
- 반올림 순서: 항목별로 반올림한 뒤 합산하는 경우와 합산한 뒤 반올림하는 경우는 결과가 다릅니다. 분할·환불·부분취소에서 나눈 금액의 합이 원금과 같은지도 확인하세요.
- 통화별 소수 자릿수: KRW·JPY는 0자리, USD는 2자리, BHD·KWD는 3자리입니다. 자릿수를 2로 하드코딩하지 않았는지 보세요.
- 경계값 테스트 후보: x.5 / x.005, 음수(환불), 0, 매우 큰 금액, 할인율과 세율이 겹치는 경우, 1/3처럼 나누어떨어지지 않는 분할.
