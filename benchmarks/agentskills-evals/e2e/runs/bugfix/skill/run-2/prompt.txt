결제 모듈에서 가끔 금액의 소수점 반올림 결과가 틀리는 버그를 찾아 고쳐 주세요. 금액이 1원/1센트만 틀려도 정산 불일치나 고객 과금 오류가 생기므로, 증상만 덮지 말고 근본 원인을 고치는 것이 목표입니다.

<context>
- 저장소/모듈 위치: {결제 모듈 경로 — 모르면 코드베이스에서 직접 찾을 것}
- 재현 사례: {틀린 금액 예시가 있으면 입력값·기대값·실제값 / 없으면 "없음"}
- 반올림 정책: {예: 원 단위 반올림(ROUND_HALF_UP), 은행가 반올림(HALF_EVEN), 절사 등 / 모르면 "미정"}
- 지원 통화: {예: KRW, USD, JPY / 모르면 코드에서 확인}
</context>

<process>
1. 먼저 금액이 생성·변환·계산·반올림·직렬화되는 경로를 끝까지 추적하세요. 입력 파싱 → 할인/세금/수수료/분할 계산 → 반올림 → DB 저장 → API 응답·PG 전송까지 포함합니다.
2. 수정하기 전에 버그를 재현하는 실패 테스트를 먼저 작성하세요. 재현 사례가 없으면 아래 경계값으로 직접 찾아내세요.
3. 원인을 하나로 특정한 뒤 고치세요. 원인 후보가 여러 개라면 각각을 테스트로 확인하고, 실제로 증상을 만드는 것만 수정합니다.
4. 수정 후 새 테스트와 기존 테스트 전체를 실행해 통과를 확인하세요.
</process>

<likely_causes>
"가끔" 틀린다는 점은 특정 값에서만 드러나는 정밀도 문제를 시사합니다. 다음을 특히 확인하세요.
- float/double로 금액을 다루는 곳. 예: 1.005 * 100 = 100.49999…라서 반올림하면 100이 됩니다.
- float에서 Decimal/BigDecimal로 넘길 때의 정밀도 손실. Decimal(0.1)이나 new BigDecimal(0.1)처럼 float로 생성하면 이미 오차가 들어간 값이 됩니다. 문자열이나 정수 최소단위로 생성해야 합니다.
- 언어 기본 반올림 함수의 규칙 차이. Python round()와 Java의 일부 기본값은 HALF_EVEN이고, JS Math.round는 음수에서 -2.5 → -2가 됩니다.
- 중간 계산마다 반올림하는 경우와 마지막에 한 번만 반올림하는 경우가 섞여 있는 곳. 항목별 반올림의 합과 합계의 반올림이 달라질 수 있습니다.
- 통화별 소수 자릿수(KRW·JPY는 0자리, USD는 2자리 등)가 하드코딩되어 있거나 무시되는 곳.
- 분할 결제·환불·할부에서 나머지 금액 배분이 누락되어 합계가 원금과 맞지 않는 곳.
</likely_causes>

<test_cases>
최소한 다음 경계값을 테스트에 포함하세요: 0.005, 0.015, 1.005, 2.675, 0.125(HALF_EVEN과 HALF_UP 결과가 다른 값), 음수 금액(환불), 0, 매우 큰 금액(예: 9,999,999,999.995), 3으로 나눠떨어지지 않는 분할(예: 100 ÷ 3), 소수 자릿수가 0인 통화.
</test_cases>

<constraints>
- 반올림 정책이 코드·문서 어디에도 정의되어 있지 않거나 위치마다 서로 다르면, 임의로 하나를 고르지 말고 발견한 내용을 정리해 보고하고 멈추세요. 정책 결정은 사람이 해야 합니다.
- 기존 테스트의 기대값은 수정하지 마세요. 기대값 자체가 틀렸다고 판단되면 근거와 함께 보고만 하세요.
- DB 스키마(컬럼 타입·정밀도) 변경, 외부 API·PG 연동 규격 변경, 공개 인터페이스 시그니처 변경이 필요하면 구현하지 말고 제안으로 보고하세요.
- 실제 PG·결제 API 호출, 운영 DB나 운영 로그 접근은 하지 마세요. 테스트는 목(mock)과 로컬 데이터로만 진행합니다.
- commit, push, 배포는 하지 마세요. 변경은 작업 트리에만 남깁니다.
- 수정 범위는 이 버그로 한정하세요. 관련 없는 리팩터링이나 포맷 변경은 하지 마세요. 같은 원인의 버그를 다른 위치에서 발견하면 함께 고치되 보고서에 따로 표시하세요.
- 작업 중 만든 임시 파일과 스크립트는 끝나면 삭제하세요.
</constraints>

<done_when>
- 버그를 재현하던 테스트가 수정 전에는 실패하고 수정 후에는 통과한다.
- 위 경계값 테스트와 기존 테스트가 모두 통과한다.
- 금액 계산 경로에서 float/double을 거치는 곳이 남아 있지 않거나, 남아 있다면 그 이유를 보고서에 적었다.
</done_when>

2. 수정 내용: 변경한 파일과 변경 요지
3. 테스트: 추가한 테스트 목록과 전체 테스트 실행 결과(실패가 있으면 출력 그대로)
4. 보고만 하고 하지 않은 것: 정책 결정, 스키마나 연동 변경 제안, 기대값이 의심되는 기존 테스트
5. 미확인 사항: 검증하지 못한 가정
</report>
