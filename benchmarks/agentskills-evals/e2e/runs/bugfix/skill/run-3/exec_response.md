## 1. 근본 원인

`payment/money.py:8` `round_amount`가 `return round(float(value), 2)` 였고, 이 한 줄에 원인이 세 가지 겹쳐 있었습니다.

| 원인 | 메커니즘 | 재현 입력 → 실제 / 기대 |
|---|---|---|
| float의 이진 근사 | 2.675는 실제로 2.67499999…로 저장됨 | 2.675 → 2.67 / **2.68**, 1.005 → 1.0 / **1.01** |
| 파이썬 `round()`는 half-even | 정확히 표현되는 .5도 짝수 쪽으로 감 | 0.125 → 0.12 / **0.13**, -0.125 → -0.12 / **-0.13** |
| 자릿수를 2로 고정 | `currency` 인자를 무시함 | KRW 100.5 → 100.5 / **101** (원 단위 아래가 남음) |

같은 패턴이 다른 곳에도 있었습니다.
- `payment/money.py:13` `apply_rate`: `amount * rate`를 float로 곱함. 0.7×1.5 → 1.04 (기대 1.05)
- `payment/cart.py:6` `line_total`: 1.005×3 = 3.0149999… → 3.01 (기대 3.02)
- `payment/cart.py:14,19` `cart_total`: float로 누적. 이번 입력들에서는 마지막 반올림 덕에 결과가 틀리지 않았습니다.
- `payment/cart.py:25` `refund_amount`: 2.01×0.5 → 1.0 (기대 1.01)
- `payment/money.py:18-19` `split_amount`: 나머지를 배분하지 않음. 100을 3으로 나누면 [33.33]×3이 되어 합이 99.99입니다(정책 위반).

## 2. 변경 내용 (`payment/money.py`, `payment/cart.py`)

- 내부 계산은 모두 `Decimal`로 합니다. float 입력은 `Decimal(repr(x))`로 바꿉니다(`Decimal(float)` 직접 변환은 쓰지 않음). int, str, Decimal 입력은 그대로 정확하게 받습니다.
- 반올림은 `quantize(..., ROUND_HALF_UP)`이고 자릿수는 `CURRENCY_DECIMALS`에서 가져옵니다. Decimal의 HALF_UP은 0에서 먼 쪽이므로 음수(환불)도 정책과 맞습니다.
- 곱셈(단가×수량, 금액×비율)과 장바구니 누적도 Decimal로 합니다.
- `split_amount`는 최소 단위 정수로 나누고, 나머지를 앞 순번부터 1단위씩 더합니다. `parts`가 0 이하면 `ValueError`를 냅니다.
- 공개 함수의 반환형은 기존 테스트와 호출부 호환을 위해 float으로 유지했습니다. 반환값은 반올림된 십진 금액에 가장 가까운 double입니다.
- 보정값을 더하는 식의 우회는 쓰지 않았습니다. `gateway.py`는 건드리지 않았고 호출도 하지 않았습니다.

## 4. 결정이 필요한 사항

1. **음수 분할 방향.** 정책 문서에 정해져 있지 않아 테스트에 `UNCONFIRMED_POLICY`로 표시했습니다. 지금은 절댓값 기준이라 -100을 3으로 나누면 [-33.34, -33.33, -33.33]입니다. 다른 선택지는 문자 그대로 "+1단위"를 더해서 [-33.33, -33.33, -33.34]로 만드는 것입니다. 어느 쪽이든 합은 같고, 앞 순번 고객에게 환불되는 금액만 달라집니다.
2. **지원하지 않는 통화의 처리 방식이 바뀌었습니다.** 예전에는 아무 통화나 소수 2자리로 조용히 처리했지만 이제는 `ValueError`를 냅니다. 잘못된 청구를 막기 위한 선택이었는데, `"usd"` 같은 소문자나 미등록 통화(KWD 등)를 넘기는 호출부가 있으면 깨집니다. KWD처럼 3자리 통화를 지원하려면 `CURRENCY_DECIMALS`에 추가해야 합니다.
3. **할인·세금 적용 단위.** 정책 문장은 "줄별"과 "장바구니 전체" 두 가지로 읽힐 수 있습니다. 기존 코드와 "합계 = 줄 합계의 합" 문구를 근거로 줄별 적용을 유지했습니다. 장바구니 전체에 한 번 적용하는 방식이라면 총액이 최소 단위 몇 개만큼 달라질 수 있습니다.
4. **반환형 float.** 기존 기대값(`== 10.12`)을 유지하려고 float으로 반환합니다. 그래서 호출부가 결과를 float로 다시 계산하면 오차가 또 생길 수 있습니다. 근본적으로는 반환형을 Decimal이나 최소 단위 정수로 바꾸는 게 맞지만, 함수 시그니처와 PG 요청 형식에 영향이 있어 이번에는 바꾸지 않았습니다.
5. 기존 테스트 기대값 중에 틀린 것은 없었습니다.

## 5. 같은 위험이 남은 위치

- `payment/gateway.py:8` `charge(amount, …)`: 금액을 float 그대로 받아 문자열로 만듭니다. PG에는 최소 단위 정수나 고정 자릿수 문자열로 보내는 게 안전합니다. 다만 PG 요청 형식이 바뀌는 일이라 손대지 않고 필요성만 보고합니다.
- **정밀도 한계:** float 입력은 유효숫자 약 15자리까지만 정확합니다. 예를 들어 USD로 10조 원대 이상인 17자리 금액은 float로 받는 순간 이미 값이 틀어지므로, 그런 금액은 str이나 Decimal로 넘겨야 합니다.
- 저장소에는 DB나 스키마 코드가 없어서 금액 컬럼 타입은 확인하지 못했습니다. 운영 쪽 컬럼이 FLOAT 계열이라면 DECIMAL이나 정수 최소 단위로 바꾸는 것을 검토해야 합니다.
