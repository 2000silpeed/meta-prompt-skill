## 이번 작업의 범위

   - `tsconfig.json`: `allowJs: true`로 두고, `strict`는 처음부터 켜는 것을 기본으로 합니다. 레거시 JS 파일 때문에 strict가 막히면 JS 쪽에서는 `checkJs`를 끈 채로 둡니다.

## 지켜야 할 원칙
- **동작 보존이 최우선입니다.** 변환은 타입을 붙이는 작업이지 리팩터링이 아닙니다. 로직, 에러 메시지, 응답 형태, 상태 코드를 바꾸지 마세요.
- **변환하다 버그나 이상한 코드를 발견하면 고치지 말고 기록하세요.** 예: null일 수 있는 값을 그냥 쓰는 경우, 타입이 섞이는 경우. 타입이 실제 런타임 동작을 정직하게 표현하게 하고, 발견한 것은 최종 보고에 목록으로 남겨 주세요. 수정 여부는 우리가 판단합니다.
- **테스트를 통과시키려고 테스트를 바꾸지 마세요.** 테스트 파일을 `.ts`로 옮기는 것은 괜찮지만 assertion의 의미가 바뀌면 안 됩니다. 테스트가 깨지면 원인은 변환한 코드 쪽에 있다고 보고 찾아 주세요.
- **`any` 정책**
  - 경계에서 들어오는 값(요청 body, 외부 API 응답, DB 결과)은 `unknown`이나 명시적인 타입으로 받습니다.

  - `@ts-ignore`는 쓰지 마세요. 꼭 필요하면 `@ts-expect-error`에 이유를 붙입니다.
- **Express 타입**: `req.user` 같은 커스텀 속성은 파일마다 캐스팅하지 말고, 한 곳에서 declaration merging으로 정의합니다.
- **의존성**: `typescript`, `@types/*`, jest 변환기처럼 마이그레이션에 필요한 것만 추가합니다. 기존 패키지 버전 업그레이드나 다른 라이브러리로의 교체는 하지 마세요. 꼭 필요하다고 판단되면 하지 말고 보고에 적어 주세요.

몇 가지 설계 의도를 덧붙입니다.

- **범위를 "기반 세팅 + 말단 묶음 하나"로 잘랐습니다.** 전체 변환을 한 번에 맡기면 리뷰할 수 없는 크기의 PR이 나옵니다. 첫 결과를 보고 원칙을 조정한 뒤 다음 묶음을 같은 프롬프트로 이어서 맡기는 편이 안전합니다.
- **"버그를 발견하면 고치지 말고 기록"을 명시했습니다.** 타입을 붙이다 보면 숨은 null 처리 문제가 반드시 드러나고, 모델은 이걸 자연스럽게 고치려 합니다. 하지만 마이그레이션 PR에 동작 변경이 섞이면 운영 사고가 났을 때 원인을 추적하기 어렵습니다.
- 배포 방식(Docker 등)과 PR 생성 여부는 팀마다 달라서 빈칸으로 남겼습니다. 이 두 칸은 꼭 채워 주시는 것이 좋습니다.
