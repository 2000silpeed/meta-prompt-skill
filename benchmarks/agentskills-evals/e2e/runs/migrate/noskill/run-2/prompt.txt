# 작업: 레거시 Express API 서버를 TypeScript로 점진 마이그레이션

## 배경
이 저장소는 JavaScript로 작성된 Express API 서버이고 운영 중입니다. 테스트는 jest, CI는 GitHub Actions입니다. TypeScript로 옮기려는 이유는 타입으로 버그를 미리 잡고 리팩터링을 안전하게 하기 위해서입니다. 서버는 마이그레이션하는 동안에도 계속 배포되므로, **모든 중간 단계에서 서버가 빌드되고 테스트가 통과하고 기존과 똑같이 동작해야 합니다.** 한 번에 전부 바꾸는 방식은 쓰지 않습니다.

- 저장소: [경로 또는 URL]
- 작업 브랜치: [예: `chore/ts-migration`]. 기본 브랜치에 직접 커밋하지 마세요.
- Node 버전과 패키지 매니저는 저장소에 이미 정해진 것(`.nvmrc`, `engines`, lockfile)을 그대로 따르세요.

## 먼저 현재 상태 파악하기 (코드 변경 전)
1. 디렉터리 구조, 엔트리 포인트, 모듈 시스템(CommonJS인지 ESM인지), 빌드와 실행 스크립트, jest 설정, `.github/workflows/*`를 읽으세요.
2. 지금 상태에서 테스트를 실행하고 결과를 기록하세요. **변경 전부터 실패하는 테스트가 있으면 고치지 말고 목록만 남기세요.** 마이그레이션 때문에 생긴 실패와 섞이지 않게 하려는 것입니다.
3. 의존성 그래프를 보고 다른 모듈에 의존하지 않는 말단 모듈(유틸, 상수, 설정, 모델)부터 라우트·미들웨어·앱 진입점 순서로 변환 계획을 세우세요. 계획은 `MIGRATION_PLAN.md`로 저장소에 남겨 주세요.

## 기반 설정 (첫 번째 단계, 별도 커밋)
- `typescript`와 필요한 `@types/*`(node, express, jest 및 실제로 쓰는 라이브러리)를 devDependencies에 추가하세요.
- `tsconfig.json` 설정:
  - `allowJs: true`로 JS와 TS가 섞여 있어도 빌드되게 합니다.
  - `strict: true`로 시작하세요. 기존 JS 파일에는 `checkJs`를 켜지 않아도 됩니다. 새로 `.ts`로 바꾼 파일만 strict를 만족하면 됩니다.
  - 현재 모듈 시스템을 유지하세요. CJS를 ESM으로 바꾸는 일은 이 작업 범위에 넣지 마세요.
- jest가 `.ts`를 실행하도록 `ts-jest`나 `@swc/jest` 중 하나를 고르고, 고른 이유를 한 줄로 적어 주세요. 기존 `.js` 테스트도 그대로 돌아가야 합니다.
- 빌드 결과물(예: `dist/`)과 실행 스크립트(`start`, `dev`)를 정리하세요. 운영 실행 방식(Dockerfile, Procfile, PM2 설정 등)이 있다면 빌드 결과물을 가리키도록 함께 고치세요. 무엇을 바꿨는지 반드시 보고해 주세요.
- GitHub Actions에 `tsc --noEmit`(또는 `npm run typecheck`) 단계를 추가하고, 기존 테스트 단계는 그대로 두세요.
- 이 단계가 끝나면 `.ts` 파일이 하나도 없는 상태에서 빌드, 테스트, 타입체크가 모두 통과해야 합니다.

## 파일 변환 규칙
- 한 커밋에는 서로 관련된 작은 묶음(대략 1~5개 파일)만 넣으세요. 각 커밋 시점마다 빌드, 테스트, 타입체크가 통과해야 합니다. 문제가 생겼을 때 해당 커밋만 되돌릴 수 있게 하려는 것입니다.
- 이름 변경은 `git mv`로 하세요. 그래야 히스토리가 남습니다.
- **런타임 동작을 바꾸지 마세요.** 응답 형태, 상태 코드, 에러 메시지, 미들웨어 순서, 환경변수 처리가 모두 같아야 합니다. 타입을 붙이다가 실제 버그를 발견하면 그 자리에서 고치지 말고 `// TODO(ts-migration): ...` 주석을 달고 보고서에 기록하세요. 버그 수정과 마이그레이션이 섞이면 리뷰하기 어렵습니다.
- 타입 작성 기준:
  - `any`는 쓰지 마세요. 정말 타입을 알 수 없는 외부 입력(`req.body` 등)에는 `unknown`을 쓰고, 기존에 검증 로직이 있으면 그 지점에서 타입을 좁히세요.
  - 피할 수 없을 때만 `// eslint-disable-next-line` 또는 `as` 단언을 쓰고, 이유를 주석으로 남기세요.
  - `req.user` 같은 Express 확장 속성은 `types/express.d.ts`에서 module augmentation으로 선언하세요.
  - 여러 파일에서 같이 쓰는 도메인 타입은 `src/types/`에 모아 두세요.
- 테스트 파일은 소스 파일을 옮긴 다음에 `.ts`로 옮겨도 됩니다. **테스트의 검증 내용(assertion)을 바꿔서 통과시키지 마세요.** import 경로와 타입만 고칠 수 있습니다. assertion을 바꿔야만 하는 상황이면 멈추고 보고하세요.
- 새 런타임 의존성은 추가하지 마세요. devDependency(타입 패키지, 빌드 도구)만 허용합니다.

## 확인 방법
매 커밋 전에 다음을 실행하세요.
- `tsc --noEmit`
- 전체 jest 테스트. 결과를 처음에 기록한 기준선과 비교하세요.
- 빌드 후 서버가 실제로 뜨는지 확인하세요. `node dist/...`로 실행한 뒤 헬스체크나 대표 엔드포인트 1~2개를 curl로 호출하면 됩니다. 테스트가 덮지 못하는 부분(모듈 경로, 정적 파일 경로, `__dirname` 등)이 여기서 자주 깨집니다.
