```text
<context>
우리 팀의 레거시 Express API 서버(JavaScript)를 TypeScript로 점진 마이그레이션하려고 한다.
- 테스트: jest 테스트 약 120개. 현재 통과하는 테스트가 동작을 보증하는 기준이다.
- CI: GitHub Actions
- 서비스는 운영 중이다. 그래서 마이그레이션 내내 언제 멈추더라도 main에 배포할 수 있는 상태여야 한다.
  "한 번에 전부 TS로 다시 작성하기"는 이 목표와 맞지 않는다.
- 저장소 경로: {REPO_PATH}
- 작업 브랜치·PR 규칙: {BRANCH_POLICY — 예: migrate/ts-* 브랜치에서 모듈 묶음마다 PR, main 직접 push 금지}
</context>

<goal>
JS 소스를 TypeScript로 옮긴다. 외부에서 보이는 API 동작(라우트, 상태 코드, 응답 형태, 에러 메시지)은 바뀌지 않아야 한다.
작업은 여러 세션에 걸칠 수 있다. 각 세션은 다음 세션이 이어받을 수 있는 상태로 끝낸다.
</goal>

<instructions>
1. 착수 전 조사 (코드는 고치지 않는다)
   - package.json, 모듈 시스템(CommonJS/ESM), Node 버전, jest 설정, .github/workflows/*를 읽는다.
   - 테스트 전체를 한 번 돌려 기준선을 기록한다. 통과 수, 실패 수, 실패한 테스트 이름, 실행 시간을 남긴다.
     처음부터 실패하던 테스트는 마이그레이션 탓이 아니다. 기록만 하고 고치지 않는다.
   - 모듈 의존 그래프를 파악해 마이그레이션 순서를 정한다. 의존성이 적은 말단 모듈(유틸, 상수, 모델)부터 시작해서
     라우터·앱 진입점은 마지막에 둔다.

2. 공존 기반 구축 (첫 PR)
   - typescript, @types/node, @types/express, @types/jest 같은 필요한 타입 패키지와 TS를 처리하는 jest 변환기를 추가한다.
     ts-jest와 babel/swc 중 기존 설정에 맞는 쪽을 고르고, 고른 이유를 PR에 적는다.
   - tsconfig는 allowJs: true, checkJs: false로 시작해서 JS와 TS가 함께 빌드되게 한다.
     strict는 처음부터 켜되, 옮기지 않은 JS 파일에는 적용되지 않게 한다.
     strict를 꺼야만 진행되는 상황이면 꺼야 하는 이유와 다시 켤 계획을 progress 파일에 남긴다.
   - CI에 `tsc --noEmit` 타입체크 단계를 추가한다. 기존 테스트 단계와 실행 명령은 바꾸지 않는다.
   - 이 PR에서는 소스 파일을 하나도 변환하지 않는다. 그래야 문제가 생겼을 때 원인이 설정인지 변환인지 구분할 수 있다.

3. 모듈 단위 변환 (반복)
   - 한 PR에서는 서로 관련된 파일 몇 개(대략 1~5개)만 .js에서 .ts로 바꾼다. 리뷰어가 diff를 한 번에 읽을 수 있는 크기여야 한다.
   - 이름 바꾸기, 타입 추가, 필요한 최소한의 구문 변경(require→import 등)만 한다.
     리팩터링, 로직 수정, 포맷 변경, 의존성 업그레이드는 하지 않는다. 버그를 발견하면 고치지 말고 progress 파일의 "발견한 문제"에 적는다.
     동작 변경이 섞이면 테스트 회귀가 생겼을 때 원인을 가려낼 수 없기 때문이다.
   - any는 경계(외부 입력, 타입이 없는 라이브러리)에서만 쓰고, 쓸 때마다 `// TODO(ts-migration): 이유` 주석을 단다.
     @ts-ignore 대신 @ts-expect-error와 이유를 쓴다.
   - req/res 확장(req.user 등)은 선언 병합 파일 한 곳에 모은다.
   - 테스트 파일은 소스를 모두 옮긴 뒤에 변환한다. 테스트 assertion은 수정하지 않는다.
     테스트를 바꿔야 통과하는 상황이면 변환이 동작을 바꿨다는 신호다. 원인을 찾아 소스를 고친다.
   - 각 PR을 올리기 전에 테스트 전체, `tsc --noEmit`, 기존 lint를 실행한다.
     통과/실패 수가 기준선과 같은지 실제 실행 결과로 확인한다.

4. 마무리 단계
   - JS 소스가 남지 않으면 테스트 파일을 변환하고, allowJs를 끄고, 빌드·실행 스크립트를 컴파일 산출물 기준으로 바꾼다.
   - 남은 TODO(ts-migration) 목록을 정리한다.
</instructions>

<state_tracking>
작업 상태는 저장소 루트의 MIGRATION_PROGRESS.md에 유지한다. 각 작업 단위가 끝날 때마다 갱신하고, 세션을 시작할 때 이 파일부터 읽는다.
- 기준선 테스트 결과
- 모듈 목록과 상태(대기/진행/완료), 그리고 각 모듈의 PR 링크
- 내린 설정 결정과 이유
- 발견한 문제(버그, 테스트 공백, 타입이 없는 의존성)
- 다음에 할 일 1~3개
</state_tracking>

<autonomy>
아래 경우가 아니면 질문하지 말고 스스로 판단해 계속 진행한다.

멈추고 보고할 조건:
- 기준선 대비 테스트가 새로 실패하는데, 같은 원인으로 두 번 시도해도 해결되지 않을 때
- 런타임 동작을 바꿔야만 타입이 맞는 경우 (예: 실제로 undefined가 흘러 다니는 경로)
- 의존성 메이저 업그레이드, Node 버전 변경, 배포 스크립트·환경변수 변경이 필요할 때
- main 브랜치 push, PR 머지, CI 시크릿이나 브랜치 보호 규칙 변경 같은 되돌리기 어려운 작업이 필요할 때.
  이런 작업은 하지 않고, 필요하다는 사실만 보고한다.

독립적인 조사(여러 파일 읽기, 타입 정의 패키지 존재 확인 등)는 도구를 병렬로 호출해도 된다.
</autonomy>

<done_criteria>
각 PR의 완료 조건:
- 테스트 통과/실패 수가 기준선과 같다 (실제 실행 출력으로 확인)
- `tsc --noEmit` 통과
- 새 any와 @ts-expect-error에 모두 이유가 달려 있다
- MIGRATION_PROGRESS.md가 갱신되어 있다

전체 완료 조건:
- src 아래에 .js 소스가 없다
- allowJs 없이 strict 빌드가 통과한다
- CI가 green이다

"완료했다"고 말하는 근거는 직접 실행한 명령의 결과뿐이다. 실행하지 못한 검증은 실행하지 못했다고 쓴다.
</done_criteria>

<report_format>
세션이 끝날 때 아래 내용을 짧게 보고한다.
- 이번 세션에 변환한 모듈과 PR
- 테스트/타입체크 결과 (명령과 수치)
- 멈춘 이유 (해당할 때)
- 다음 세션이 할 일
</report_format>
```

**API/실행 권고**
- model: `claude-opus-5-5`
- effort: 장기 코딩 작업이므로 `high`를 권장합니다. Opus 5.5의 기본값은 medium입니다. 비용이 부담되면 2단계까지는 high로 돌리고, 3단계의 반복 변환은 medium으로 비교해 보세요.
- thinking: 생략하거나 `{type: "adaptive", display: "summarized"}`로 두세요. 진행 상황을 지켜보려면 summarized가 편합니다.
- 무인 루프로 돌린다면, 모델이 말로 끝냈다고 해서 완료로 처리하지 마세요. MIGRATION_PROGRESS.md에 남은 작업이 있으면 "이어서 진행"을 보내되, 같은 작업에서는 2~3회까지만 자동으로 이어 보내고 그 뒤에는 사람이 확인하는 편이 안전합니다.

**진단**
- 명확성: 높음. 요청이 "TS 점진 마이그레이션"으로 분명합니다.
- 구체성: 낮았습니다. "점진"의 단위와 완료 기준이 없어서 PR 크기, 동작 불변 원칙, 기준선 테스트 대비 판정, PR별·전체 완료 조건을 추가했습니다.
- 맥락: 중간이었습니다. 왜 점진적으로 해야 하는지(운영 중이고 언제든 배포 가능해야 함), 여러 세션에 걸친 상태 유지, 멈춰야 하는 조건을 보강했습니다.

**적용 규칙**
- Opus 5.5는 지시를 문자 그대로 따릅니다. 그래서 "하지 마라"만 쓰지 않고 이유를 함께 적었습니다. 예를 들어 리팩터링 금지에는 "회귀가 생겼을 때 원인을 가려낼 수 없기 때문"이라는 이유를 붙였습니다.
- 맥락, 지시, 자율성 범위, 완료 기준을 XML 태그로 나눴습니다. 계속 진행할지, 멈추고 물을지는 미리 정한 조건으로 판단하게 했습니다.
- 장기 작업에서는 모델이 실제로 끝내지 않고도 완료를 주장할 수 있습니다. 그래서 완료 근거를 직접 실행한 명령 결과로 제한하고, 상태를 파일에 남겨 세션을 이어받게 했습니다.

**가정** (실행 전에 채우거나 확인할 부분)
- `{REPO_PATH}`, `{BRANCH_POLICY}`: 자리표시자입니다. 모듈 시스템(CJS/ESM)과 Node 버전은 모델이 1단계에서 직접 조사하게 했습니다.
- PR을 만들 권한은 있고, 머지와 main 직접 push는 사람이 한다고 가정했습니다.
- 프롬프트는 한국어로 작성했습니다. 팀 저장소의 커밋과 PR을 영어로 쓴다면 그렇게 하라는 한 줄을 추가하세요.

이 가이드북은 일부만 공식 문서와 대조된 상태이고, 마지막 검증일은 2026-10-12입니다. XML 구조 관련 규칙은 공식 문서와 대조하지 않은 지식 기반 초안입니다.
