# 목표
결제 모듈에서 금액의 소수점 반올림 결과가 가끔 틀리는 버그를 찾아서 고쳐라.
재현 → 원인 확인 → 최소 수정 → 실제 테스트 실행까지 끝내야 완료다.
코드만 쓰고 멈추지 마라.

# 알려진 정보
- 증상: 일부 금액에서만 반올림 결과가 1원/1센트 정도 어긋난다(항상 그런 건 아니다).
- 결제 모듈 위치: {예: src/payment/ — 모르면 직접 탐색}
- 실제로 틀렸던 사례: {예: 입력 1.005 → 기대 1.01, 실제 1.00 / 없으면 직접 찾아라}
- 테스트 실행 명령: {예: pnpm test / pytest / ./gradlew test — 모르면 프로젝트 설정 파일에서 찾아라}

# 진행 방법
1. 탐색: 결제 모듈에서 금액을 계산·변환·반올림·포맷하는 지점을 모두 찾아 목록으로 만들어라.
   특히 다음을 확인하라.
   - 금액을 float/double/JS number로 저장하거나 계산하는 곳
   - round 계열 함수(Python round()의 은행가 반올림, JS toFixed/Math.round 등)를 쓰는 곳.
     이런 함수의 반올림 방식이 의도한 규칙과 다를 수 있다.
   - 반올림 순서: 항목별로 반올림한 뒤 합산하는지, 합산한 뒤 반올림하는지.
     세금·할인·수수료·분할 결제·환불 계산에서 이 순서가 섞이지 않았는지
   - 통화별 소수 자릿수(KRW/JPY 0자리, USD 2자리 등)를 하드코딩했는지
   - 문자열 ↔ 숫자 변환, DB 컬럼 타입, 외부 PG 응답 파싱에서 정밀도가 손실되는지
2. 재현: 버그를 일으키는 입력을 찾아서, 고치기 전에 실패하는 테스트를 먼저 추가하라.
   경계값(x.xx5, 음수/환불, 0, 큰 금액, 여러 항목 합산)을 포함하라.
3. 원인 판단: 실패 원인을 코드 위치와 함께 한두 문장으로 설명하라.
4. 수정: 원인을 해결하는 가장 단순한 변경을 하라.
   금액 연산은 정확한 십진 표현을 써라. 예: Decimal/BigDecimal/정수 최소단위(원·센트), 또는 프로젝트에 이미 있는 money 유틸.
   반올림 방식과 자릿수는 명시적으로 지정하라.
   같은 패턴이 결제 모듈의 다른 곳에도 있으면 함께 고쳐라.
5. 검증: 새 테스트와 기존 테스트 스위트 전체를 실행하라. 타입 검사나 린트가 있으면 그것도 실행하라.
   실패하면 고쳐서 다시 실행하라.

# 범위와 멈출 지점
- 결제 모듈과 그 테스트 안의 수정은 스스로 진행해도 된다.
- 기존 코드 규약과 프로젝트에 있는 유틸을 우선 써라. 버그와 관계없는 리팩터링·포맷 변경은 하지 마라.
- 다음 경우에는 수정하지 말고, 근거를 정리해 보고한 뒤 멈춰라.
  - 올바른 반올림 규칙(사사오입 vs 은행가 반올림, 절사 등)이 코드·문서·테스트 어디에도 정해져 있지 않아,
    정책을 새로 정해야 하는 경우.
    현재 동작과 후보 규칙, 각 규칙에서 결과가 달라지는 예시를 제시하라.
  - DB 스키마나 마이그레이션 변경이 필요한 경우
  - 외부 PG 연동 코드, API 키, 실결제 호출을 바꿔야 하는 경우
  - 이미 저장된 금액 데이터를 보정해야 하는 경우
- 실제 결제 API나 운영 DB에는 접근하지 마라.

# 완료 조건
- 수정 전에는 실패하고 수정 후에는 통과하는 재현 테스트가 1개 이상 있다.
- 기존 테스트 스위트가 모두 통과한다. 실행하지 못한 검증이 있으면 그 이유를 적는다.
- 결제 모듈에 금액용 float 연산이나 암묵적인 반올림이 남아 있지 않다.
  남겨 둔 곳이 있으면 이유를 적는다.

3. 추가한 테스트와 재현 입력
4. 실행한 검증 명령과 결과(통과/실패 그대로)
5. 남은 위험이나 사람이 결정해야 할 사항(반올림 정책, 기존 데이터 영향 등)

**원래 요청에서 보강한 점**
- **명확성**: "반올림이 틀린다"는 말이 여러 원인을 뜻할 수 있습니다. 그래서 흔한 원인을 탐색 체크리스트로 넣었습니다: float 연산, 은행가 반올림, 항목별 반올림과 합산 후 반올림의 순서, 통화별 자릿수.
- **구체성**: "고쳐줘"만으로는 언제 끝났는지 알 수 없습니다. 그래서 실패하는 재현 테스트를 먼저 쓰고, 고친 뒤 전체 테스트가 통과해야 완료되도록 했습니다.
- **맥락**: 저장소 경로, 언어, 실제로 틀렸던 사례를 몰라서 `{ }` 자리로 남겼습니다. 비워 두면 GLM이 직접 찾습니다.

**GLM에 맞춘 부분**
- GLM-5.3은 긴 작업을 혼자 끝까지 할 때 강합니다. 그래서 코드 조각을 달라고 하지 않고, 원인 파악부터 수정, 테스트 실행, 보고까지 통째로 맡겼습니다.
- 결제 모듈 안의 되돌릴 수 있는 수정은 스스로 진행하게 했습니다. 반올림 규칙을 새로 정해야 할 때, DB나 PG 연동을 바꿔야 할 때, 저장된 데이터를 고쳐야 할 때만 멈추고 보고하게 했습니다. 반올림 규칙은 코드가 아니라 회사가 정할 문제라서, GLM이 임의로 정하지 않게 하려는 것입니다.
- 실행하지 못했거나 실패한 검증도 그대로 보고하게 했습니다.

**설정**
- 모델은 `glm-5.3`을 쓰고, `reasoning_effort`는 기본값 `max`를 그대로 두면 됩니다. 디버깅 작업이고 반복 호출이 많은 루프가 아니기 때문입니다.
- Coding Plan을 한 번이라도 구독했다면(만료된 구독 포함) GLM-5.3 API는 OpenAI Chat Completion 호환 엔드포인트로만 쓸 수 있습니다. 주소는 `https://api.z.ai/api/coding/paas/v4`입니다. 직접 API로 붙일 때만 해당하고, 코딩 에이전트 도구 안에서 쓴다면 신경 쓰지 않아도 됩니다.

**가정**: 코딩 에이전트 도구 안에서 실행한다고 보고 썼습니다. 또 실결제 API와 운영 DB에는 접근하지 않는 것으로 정했습니다.
