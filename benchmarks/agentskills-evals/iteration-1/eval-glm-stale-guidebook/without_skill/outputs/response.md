# 작업: 결제 모듈의 금액 소수점 반올림 버그 수정

## 배경
결제 모듈에서 가끔 금액 반올림 결과가 틀린다. 항상 틀리는 게 아니라 특정 금액이나 조건에서만 틀린다.
- 증상 예시: [예: 19.995 → 20.00이어야 하는데 19.99로 나옴 / 할인 적용 후 총액이 1원 차이 남 / 없으면 이 줄 삭제]
- 관련 위치 추정: [예: src/payment/, PriceCalculator, 없으면 삭제]
- 언어/스택: [예: TypeScript, Java/Spring, Python, 없으면 삭제]

## 목표
반올림 오류의 **근본 원인**을 찾아 고친다. 증상만 가리는 보정 코드(예: +0.0001 더하기, 특정 금액 하드코딩)는 금지한다.

## 진행 순서 (이 순서대로 진행할 것)

### 1. 조사 (아직 코드 수정 금지)
결제 금액이 계산·변환·저장·표시되는 경로를 모두 찾아라. 특히 아래 패턴을 grep으로 전수 조사한다.
- 금액을 부동소수점(float/double/JS number)으로 다루는 곳
- `Math.round`, `round()`, `toFixed`, `Math.floor/ceil`, `parseFloat`, `BigDecimal(double)` 생성자, `setScale` 호출, `RoundingMode`, `Decimal`의 quantize/context 설정
- 같은 금액을 여러 번 반올림하는 곳 (중간 단계 반올림 + 최종 반올림)
- 세금·할인·수수료·분할결제·환불처럼 금액을 곱하거나 나누는 곳
- 통화별 소수 자릿수 처리 (KRW/JPY는 0자리, USD는 2자리, KWD/BHD는 3자리)
- 음수 금액(환불, 차감)의 반올림 방향

### 2. 반올림 정책 확인
이 프로젝트가 의도하는 반올림 규칙을 코드, 주석, 문서, 기존 테스트, PG사 연동 스펙에서 찾아라.
- 반올림 모드: HALF_UP(사사오입), HALF_EVEN(은행가 반올림), 절사 중 무엇인가
- 반올림 시점: 항목별로 하는가, 합계에서 한 번만 하는가
- 정책이 문서화되어 있지 않거나 코드 안에서 서로 다른 정책이 섞여 있으면, **임의로 하나를 고르지 말고** 발견한 내용을 정리해 보고한 뒤 멈춰라.

### 3. 재현 테스트 먼저 작성
버그를 재현하는 실패 테스트를 먼저 작성하고 실제로 실패하는 것을 확인한다. 최소한 아래 경우를 포함한다.
- 이진 부동소수점으로 정확히 표현되지 않는 경계값: 1.005, 2.675, 0.125, 19.995, 1.015
- 정확히 .5인 경계값과 그 음수 버전(-1.005, -0.5)
- 0원, 최소 단위(0.01 / 1원), 아주 큰 금액(예: 99,999,999.995)
- 소수 자릿수가 0자리인 통화와 3자리인 통화
- 할인율·세율 적용 후의 금액, 금액을 N개로 나눴을 때 나눈 금액의 합이 원래 금액과 같은지
- 버그를 재현하지 못하면 그 사실을 보고하고, 추측으로 수정하지 마라.

### 4. 수정
- 금액 계산은 정수 최소 단위(원·센트) 또는 10진수 타입(BigDecimal, Python Decimal, decimal.js/big.js 등 **프로젝트에 이미 있는 것** 우선)으로 처리한다.
- BigDecimal은 double이 아니라 문자열에서 생성한다(`new BigDecimal("1.005")` 또는 `BigDecimal.valueOf`).
- 반올림은 정해진 시점에 한 번만, 2단계에서 확인한 정책대로 수행한다.
- 반올림 로직이 여러 곳에 흩어져 있으면 하나의 함수로 모아서 재사용하게 한다. 단, 버그와 관계없는 대규모 리팩터링은 하지 마라.
- 새 의존성 추가는 꼭 필요할 때만 하고, 추가했다면 이유를 보고서에 적는다.

### 5. 검증
- 3단계에서 만든 테스트를 포함해 전체 테스트를 실행하고 모두 통과하는지 확인한다.
- 수정 때문에 기존 테스트의 기대값이 바뀌어야 한다면, 그 테스트는 바꾸지 말고 목록으로 보고하라. 기존 동작이 틀렸던 것인지 의도된 것인지는 사람이 판단한다.
- 린트와 타입 체크도 통과시킨다.

## 금지 사항

- 외부 API(PG사)로 주고받는 요청·응답 형식 변경 금지
- public 함수의 시그니처 변경 금지 (불가피하면 보고)
- 실제 결제 API 호출, 운영 환경 설정 파일 수정, 시크릿 접근 금지
- git commit/push 금지. 변경 사항은 작업 트리에만 남긴다.

**이렇게 만든 이유**
- **조사부터 시키고 수정은 나중에:** GLM 계열 에이전트는 바로 `toFixed` 하나만 고치고 끝내는 경향이 있습니다. 그래서 단계 순서를 강제하고, 실패 테스트를 먼저 쓰게 했습니다.
- **반올림 정책이 불명확하면 멈추기:** HALF_UP과 HALF_EVEN을 모델이 마음대로 고르면 정산 금액이 틀어질 수 있습니다. 그래서 정책을 확인할 수 없으면 보고하고 멈추도록 했습니다.
- **기존 테스트 기대값은 고치지 않고 보고만:** 에이전트가 테스트를 고쳐서 통과시키는 것을 막기 위해서입니다.
- **증상 예시를 하나라도 채우면 정확도가 크게 올라갑니다.** 로그에 찍힌 실제 금액 한 건만 있어도 충분합니다.
