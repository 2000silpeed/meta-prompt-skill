<context>
레거시 Express API 서버(JavaScript)를 TypeScript로 점진 마이그레이션한다. 이 서버는 운영 중이므로,
마이그레이션 내내 언제 끊어도 main에 머지 가능한 상태를 유지해야 한다.
- 테스트: jest 약 120개. 현재 통과 상태를 기준선(baseline)으로 삼는다.
- CI: GitHub Actions (.github/workflows/ 아래)
- 이 작업은 여러 세션에 걸친 장기 작업이다. 이전 세션의 기억은 남지 않으므로,
  진행 상태는 저장소 안의 파일(MIGRATION.md)로만 이어진다.
</context>

<goal>
런타임 동작을 바꾸지 않고 src의 .js 파일을 .ts로 옮기고, 최종적으로 `strict: true`에서
타입 오류 0을 만든다. 성공 기준:
1. 모든 단계에서 jest 전체 통과 (테스트 수가 baseline보다 줄지 않음)
2. `tsc --noEmit` 통과, CI에 타입 체크 job 추가·통과
3. 서버가 빌드 산출물로 기동되고, 기존 엔드포인트의 요청/응답 형태가 그대로 유지됨
4. 남은 `any`·`@ts-expect-error`는 모두 MIGRATION.md에 이유와 함께 기록됨
</goal>

<phase_0_discovery>
코드를 바꾸기 전에 아래를 확인해서 MIGRATION.md 맨 위에 적는다. 이후 결정은 모두 이 사실에 근거한다.
- Node 버전, 모듈 시스템(CommonJS / ESM), 패키지 매니저와 lockfile
- 진입점, 라우터/미들웨어 구조, 파일 수와 의존 그래프(import가 적은 leaf 모듈부터 파악)
- jest 설정(transform, testMatch, setup 파일), `npm test` 실제 실행 결과 → baseline으로 기록
  (통과/실패/스킵 수. 원래 실패하던 테스트는 고치지 말고 목록만 남긴다)
- CI 워크플로가 실행하는 명령, Node 매트릭스, 캐시 설정
- 이미 있는 JSDoc 타입, @types 패키지, eslint/prettier 설정
</phase_0_discovery>

<strategy>
권장 순서다. 저장소 사실이 다르면 이유를 MIGRATION.md에 적고 조정한다.
1. 기반: typescript, @types/node, @types/express, ts-jest(또는 기존 transform에 맞는 방식)를 설치한다.
   tsconfig는 `allowJs: true`, `checkJs: false`, `strict: false`로 시작해서 JS와 TS가 섞여 있어도 돌아가게 한다.
   모듈 시스템은 지금 것을 유지한다. CJS→ESM 전환은 이번 범위가 아니다(동작 변화 위험이 커서).
2. CI: 기존 job은 건드리지 않고 `tsc --noEmit` 단계만 추가한다.
3. 변환: leaf 모듈(유틸, 상수, 모델) → 서비스 → 미들웨어 → 라우터 → 앱 진입점 순서로 진행한다.
   한 번에 하나의 응집된 묶음(대략 1~5개 파일)만 바꾸고, 바꿀 때마다 jest 전체와 tsc를 돌린다.
   rename은 `git mv`로 해서 히스토리를 남긴다.
4. 타입: 요청 body/params/query, 응답 형태, 에러 객체부터 타입을 붙인다. 모르는 타입은
   추측해서 단정하지 말고 `unknown` + 좁히기로 처리한다. 그래도 안 되면 `any`를 두고 TODO로 기록한다.
5. 엄격화: 전부 .ts가 되면 noImplicitAny → strictNullChecks → strict 순서로 하나씩 켠다.
6. 테스트 파일 변환은 소스가 끝난 뒤에 한다. 테스트의 assertion은 바꾸지 않는다.
</strategy>

<rules>
- 런타임 동작 변경 금지: 리팩터링, 로직 수정, 의존성 메이저 업그레이드는 하지 않는다. 마이그레이션 중
  찾은 버그는 고치지 말고 MIGRATION.md의 "발견 사항"에 파일:라인과 함께 적는다.
  타입 작업과 동작 변경이 섞이면 회귀가 생겼을 때 원인을 가를 수 없기 때문이다.
- 테스트를 통과시키려고 테스트를 지우거나, skip하거나, assertion을 약하게 만들지 않는다. 테스트가 깨지면
  원인을 소스 쪽에서 찾는다. 원인이 테스트 인프라(transform, 모듈 경로) 문제일 때만 jest 설정을 고친다.
- 커밋은 작게 나누고, 각 커밋 시점에 테스트와 tsc가 통과해야 한다. 메시지 형식: `ts: migrate <영역>`.
- 작업 브랜치에서 진행한다. main에 직접 push, force push, 머지는 하지 않는다. PR 생성이 허용되는
  환경이면 단계별(기반 / 영역별 변환 / 엄격화) PR로 나눈다.
- CI 워크플로는 job 추가만 한다. 기존 단계를 지우거나 secrets를 바꾸지 않는다.
- 독립적인 조회(파일 읽기, grep, 타입 정의 확인)는 툴을 병렬로 호출한다.
</rules>
