# 목표
결제 모듈에서 금액의 소수점 반올림 결과가 가끔 틀리는 버그를 찾아 근본 원인을 고쳐라.
증상을 덮는 보정 코드(예: 결과에 0.01 더하기, 특정 금액만 예외 처리)를 넣지 말고,
틀린 값이 생기는 원인을 제거해야 한다.

# 환경과 관련 맥락
- 현재 작업공간이 대상 저장소다. 먼저 결제/금액 계산 코드의 위치를 찾아라.
  우선 볼 곳: 금액·가격·세금·할인·수수료·환율·환불·분할결제를 계산하는 함수,
  금액 포맷팅/직렬화 유틸, PG사 요청 페이로드를 만드는 코드, 관련 테스트.
- 저장소에 있는 기존 규약(금액 타입, 통화별 소수 자릿수 정의, 반올림 유틸, 테스트 프레임워크,
  lint/타입 검사/빌드 명령)을 확인하고 그대로 따르라. README, CONTRIBUTING, CI 설정에서
  검증 명령을 찾아라.
- "가끔" 틀린다는 것은 특정 입력값에서만 재현된다는 뜻일 가능성이 높다. 흔한 원인 후보:
  1. 부동소수점(float/double/JS number)으로 금액을 계산하거나 저장함 (예: 1.005 → 1.00)
  2. 반올림 방식 불일치: HALF_UP, HALF_EVEN(은행가 반올림), 버림이 경로마다 섞여 있음
     (예: Python round(), Java BigDecimal 기본값, JS toFixed, DB ROUND)
  3. 반올림 시점 불일치: 항목별로 반올림한 뒤 합산하는 경로와, 합산한 뒤 반올림하는 경로가 공존함
  4. 통화별 소수 자릿수를 하드코딩함 (KRW·JPY 0자리, USD 2자리, 일부 통화 3자리)
  5. 문자열↔숫자 변환, 직렬화, DB 컬럼 정밀도(DECIMAL scale)에서 값이 잘리거나 다시 반올림됨
  6. 세금·할인·수수료를 비율로 나눌 때 나머지 단위가 사라지거나 중복됨
  위 목록은 출발점일 뿐이다. 실제 코드에서 확인한 원인만 고쳐라.

# 범위와 경계
- 허용: 금액 계산/반올림 로직 수정, 기존 금액 타입·유틸로 통일, 테스트 추가·수정,
  필요한 범위 안에서의 작은 리팩터링.
- 진행하기 전에 멈추고 보고할 것:
  - 비즈니스 반올림 정책 자체를 바꿔야 하는 경우. 예: 코드와 문서가 서로 다른 반올림 방식을
    말하거나, 어느 쪽이 맞는지 근거가 없을 때. 이때는 후보안과 각 안의 영향을 정리해서 보고하라.
  - DB 스키마나 마이그레이션 변경, 저장된 과거 데이터 보정이 필요한 경우
  - 외부 PG/결제 API 계약(요청·응답 형식)이 바뀌는 경우
- 금지: 실제 결제 API 호출, 운영 환경 설정·비밀값 변경, 관련 없는 모듈 리팩터링,
  실패하는 테스트를 삭제하거나 skip 처리하는 것.

# 진행 방식
1. 재현: 수정 전에 틀린 결과를 내는 입력값을 찾아 실패하는 테스트로 고정하라.
   경계값을 반드시 포함하라: x.xx5 형태(1.005, 2.675, 0.125 등), 0, 음수(환불),
   아주 큰 금액, 0자리 통화와 2자리 통화, 여러 항목 합산, 비율 할인·세금.
2. 원인 확인: 그 테스트가 왜 실패하는지 계산 경로를 따라가며 특정하라.
   같은 패턴을 쓰는 다른 경로가 있는지도 검색하라.
3. 수정: 가장 단순하면서 근본 원인을 없애는 해결안을 적용하라. 금액은 정수 최소단위
   또는 Decimal/BigDecimal 같은 정확한 십진 타입으로 계산하고, 반올림 방식과 시점은
   한 곳에서 명시적으로 정의해 모든 경로가 그것을 쓰게 하라.
4. 검증: 추가한 테스트와 기존 전체 테스트, 타입 검사, lint, 빌드를 실제로 실행하라.
   실패하면 원인을 고치고 다시 실행하라.

# 완료 조건
- 수정 전 실패하던 재현 테스트가 수정 후 통과한다.
- 위 경계값 케이스가 테스트에 들어 있고 모두 통과한다.
- 기존 테스트 스위트, 타입 검사, lint, 빌드가 통과한다. 실행할 수 없었던 항목은 이유와 함께 밝힌다.
- 금액 계산 경로에 float 연산이나 정책과 다른 반올림이 남아 있지 않다. 남겨둔 것이 있으면 이유를 밝힌다.

- 수정 내용: 변경 파일 목록과 각 변경의 이유
- 적용한 반올림 정책: 방식(HALF_UP 등), 시점(항목별/합계), 통화별 자릿수, 그리고 그 근거
- 검증 결과: 실행한 명령과 결과(통과/실패/미실행)
- 남은 위험·확인 필요 사항: 정책 결정이 필요한 부분, 과거 데이터 영향 여부 등

**GLM에 맞춰 바꾼 점**
- GLM-5.3은 장시간 일하는 코딩 에이전트로 쓰는 모델입니다. 그래서 재현, 원인 확인, 수정, 실제 검증, 보고까지 전 과정을 맡기는 구조로 썼습니다.
- 에이전트가 사람 개입 없이 오래 진행하므로, 언제 멈춰야 하는지를 분명히 적었습니다. 되돌릴 수 있는 코드 수정은 알아서 진행합니다. 반대로 반올림 정책 변경, DB 변경, PG 계약 변경 앞에서는 멈추고 보고합니다.
