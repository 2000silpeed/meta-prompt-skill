# 목표
결제 모듈에서 금액의 소수점 반올림 결과가 가끔 틀리는 버그를 고쳐라.
결과물은 원인을 확인하는 재현 테스트, 근본 원인을 고친 코드, 그리고 실제로 실행한 검증 결과다.

# 알려진 증상
- 항상 틀리는 게 아니라 특정 금액에서만 틀린다. 재현 금액: {예: 10.005 → 10.00으로 나옴, 기대값 10.01 / 모르면 "미확인"}
- 발생 위치: {결제 승인 / 환불 / 할인·쿠폰 / 세금 / 분할결제 / 환율 변환 중 해당하는 것, 모르면 "미확인"}
- 결제 모듈 경로: {예: src/payments/, 모르면 "저장소에서 직접 찾을 것"}

# 먼저 확인할 것 (코드 수정 전)
1. 금액이 지나가는 경로 전체에서 타입을 확인하라. float/double, 문자열→숫자 파싱, Decimal/BigDecimal, 정수 최소단위(cent·원) 중 무엇을 쓰는지 보라.
   경로는 입력 → 계산(할인·세금·수수료·환율) → 반올림 → 저장(DB 컬럼 타입) → PG 요청 → 표시다.
2. 반올림을 하는 모든 지점을 나열하라. round(), toFixed, Math.round, setScale, 포맷터, DB ROUND, 직렬화 단계까지 포함한다.
   같은 금액이 여러 번 반올림되는 곳(중간 반올림)이 있는지도 확인하라.
3. 의도된 반올림 정책을 기존 코드·문서·테스트·PG 연동 스펙에서 찾아라. 정책은 반올림 모드(HALF_UP / HALF_EVEN / 버림), 통화별 소수 자릿수, 줄 단위 반올림인지 합계 반올림인지를 말한다.
   **정책이 서로 모순되거나 어디에도 없으면 추측해서 정하지 말고, 찾은 근거를 정리해 보고한 뒤 멈춰라.**

# 실행 순서
1. 증상을 재현하는 실패 테스트를 먼저 작성하고, 실패하는 것을 실제로 확인하라.
2. 근본 원인을 고쳐라. 증상이 난 금액만 예외 처리하거나 epsilon을 더하는 식의 땜질은 금지한다.
   일반적인 방향: 금액 계산은 Decimal 계열이나 정수 최소단위로 하고, 반올림은 정책에 정해진 지점에서 한 번만 한다.
3. 아래 경계값을 테스트에 추가하라 (해당 통화·기능에 맞는 것만):
   - 반올림 경계: x.xx5 형태 (1.005, 2.675, 0.125, 0.135). float로는 1.005*100 = 100.49999…가 된다.
   - 음수·환불: -1.005, 부분 환불 합계가 원결제 금액과 같은지
   - 통화별 자릿수: KRW·JPY 0자리, USD·EUR 2자리, KWD·BHD 3자리 (지원하는 통화만)
   - 분할·배분: 100.00을 3명으로 나눌 때 합계가 정확히 100.00인지 (나머지 1단위가 어디로 가는지)
   - 할인·세율·환율 곱셈 뒤 반올림 (예: 19.99 × 0.15, 1,234원 × 환율)
   - 0, 최소단위 1개(0.01), 아주 큰 금액(예: 99,999,999.99)
   - 문자열 입력 파싱: "10.005", "1e-2", 천 단위 구분자가 있는 경우
4. 새로 추가한 테스트와 기존 결제 관련 테스트 전체를 실행하라. 프로젝트에 린트·타입 검사·빌드가 있으면 그것도 실행하라.

# 범위와 제한
- 변경은 결제 금액 계산·반올림 로직과 그 테스트로 한정한다. 관련 없는 리팩터링이나 포맷팅 변경은 하지 마라.
- 다음은 하지 말고 제안만 하라: DB 스키마·컬럼 타입 변경, 마이그레이션, 기존 저장 데이터 보정, PG 요청 형식 변경, 공개 API 응답 형식 변경.
- 실제 결제·외부 PG 호출을 하지 마라. 테스트는 mock이나 sandbox만 쓴다.
- 기존 코드 스타일과 금액 유틸(이미 있는 Money 클래스나 헬퍼)을 우선 재사용하라.

# 완료 조건
- 처음 작성한 재현 테스트가 수정 전에는 실패하고 수정 후에는 통과한다.
- 위 경계값 테스트와 기존 결제 테스트가 모두 통과한다.
- 반올림이 정책에 정한 지점에서만 일어난다는 것을 코드로 보일 수 있다.

# 보고 형식 (간결하게)

2. 변경 내용: 파일별 요약
3. 적용한 반올림 정책과 그 근거(어디서 확인했는지)
4. 실행한 검증 명령과 결과. 실패하거나 실행하지 못한 항목은 그대로 적는다.
5. 범위 밖이라 제안만 한 것 (예: DB 컬럼이 FLOAT라 기존 데이터에 오차가 있을 수 있음)

**보강한 점**
- 원래 요청은 "가끔 틀린다"뿐이었습니다. 그래서 금액이 지나가는 모든 단계의 타입과 반올림 지점을 먼저 조사하게 했습니다. 이런 버그는 보통 float 사용이나 같은 금액을 여러 번 반올림하는 데서 생깁니다.
- 반올림 정책(HALF_UP인지 HALF_EVEN인지, 줄 단위인지 합계인지)은 회사마다 다릅니다. 모델이 추측해서 정하지 않도록, 근거가 없으면 보고하고 멈추게 했습니다.
- 바로 쓸 수 있는 경계값 테스트 목록과 함께, 재현 테스트를 먼저 쓰고, 땜질은 금지하고, DB·PG 변경은 제안만 하도록 하는 규칙을 넣었습니다.

**채워야 할 것**: `{재현 금액}`, `{발생 위치}`, `{모듈 경로}`. 모르면 "미확인"으로 두면 됩니다. 재현 금액이 하나라도 있으면 결과가 크게 좋아집니다.
