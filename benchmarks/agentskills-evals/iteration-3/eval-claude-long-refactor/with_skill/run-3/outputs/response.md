<task>
레거시 Express(JavaScript) API 서버를 TypeScript로 점진 마이그레이션하라.
목표는 "외부 동작을 하나도 바꾸지 않고, 매 단계가 배포 가능한 상태로 유지되는" 변환이다.
한 번에 전부 바꾸는 빅뱅 재작성은 하지 않는다. 리뷰어가 단계별로 검토하고, 문제가 생기면 해당 단계만 되돌릴 수 있어야 하기 때문이다.
이 작업은 여러 세션에 걸친 장기 작업이며 비대화형으로 실행된다. 중간에 사람에게 질문할 수 없다.

<context>
- 저장소: {{저장소 경로 또는 URL}}

- CI: GitHub Actions (.github/workflows/)

  Node 버전, 패키지 매니저(lockfile 기준), 모듈 방식(CommonJS/ESM), 진입점과 start 스크립트,

<approach>
1. 기준선 확보: 아무것도 바꾸기 전에 설치 → 전체 jest 실행 → CI와 같은 명령 실행을 하고 결과를 기록하라.
   이미 실패하거나 간헐적으로 실패하는 테스트는 목록으로 남겨라. 그래야 이후 실패가 마이그레이션 탓인지 구분할 수 있다.
2. 공존 인프라: typescript와 필요한 @types/* 를 devDependencies로 추가하고, `allowJs: true`인 tsconfig를 만들어 JS와 TS가 섞여도 빌드·테스트가 되게 하라.
   jest가 .ts 파일을 실행하도록 설정하라(기존 설정에 맞춰 ts-jest 또는 babel 중 하나를 선택하고, 선택한 이유를 기록할 것).
   이 단계를 마친 시점에 .js 파일을 하나도 바꾸지 않은 상태로 테스트 결과가 기준선과 같아야 한다.
3. 변환 순서: 의존성 그래프의 말단부터 위로 올라가라. 보통은 utils/상수 → 모델/DB 접근 → 서비스 → 미들웨어 → 라우터 → app/server 진입점 순서다.
   실제 import 그래프를 보고 순서를 정한 뒤 진행 파일에 적어라.
4. 단위 작업 = 모듈 1개 또는 밀접한 소수 파일. 단위마다 다음을 모두 통과해야 다음으로 넘어간다:
   `tsc --noEmit` 통과 → 전체 jest 통과(기준선과 동일) → 린트(있다면) 통과 → 작업 브랜치에 커밋 1개.
5. 엄격도 상향: 처음에는 strict를 끈 상태로 시작하라. 변환 비율이 오르면 noImplicitAny → strictNullChecks → strict 순으로 켜되, 한 번에 플래그 하나씩만 켜라.
   전부 끝난 뒤 allowJs 제거를 제안하라.
</approach>

<typing_rules>
- `any`는 경계(외부 입력, 타입이 없는 라이브러리)에만 쓰고, 쓸 때마다 `// TODO(ts-migration): 이유`를 남겨라. 이 개수를 진행 파일에 집계하라.
- 타입이 실제 런타임 동작과 맞지 않으면 코드를 바꾸지 말고 타입을 실제 동작에 맞춰라. 타입을 깔끔하게 만들려고 로직을 바꾸면 동작이 변한다.
- `as` 단언과 `!` non-null 단언은 근거가 코드에 보일 때만 써라.
</typing_rules>

<pitfalls>
Express JS→TS 마이그레이션에서 자주 깨지는 지점이다. 각 단위 작업에서 확인하라.
- CommonJS 상호운용: `module.exports = fn` 을 `export default` 로 바꾸면 아직 JS로 남은 `require()` 호출부가 `.default` 없이 깨진다.
  호출부가 전부 변환되기 전까지는 `export =` 를 쓰거나 기존 export 형태를 유지하라. esModuleInterop 설정의 영향도 함께 확인하라.
- `req.user`, `req.session` 같이 미들웨어가 붙이는 속성은 `declare global { namespace Express { interface Request {...} } }` 선언 병합으로 정의하라. 핸들러마다 `any` 캐스팅하지 마라.
- 에러 핸들러는 인자 4개 시그니처 `(err, req, res, next)` 로 Express가 식별한다. 사용하지 않는 `next`를 지우면 에러 핸들러로 인식되지 않는다.
- 타입은 런타임 입력을 검증하지 않는다. `req.body`를 타입으로 선언해도 실제 검증이 생기지는 않는다. 그렇다고 이 작업에서 검증 로직을 새로 추가하지는 마라(동작 변경). 필요해 보이면 보고 항목에 적어라.
- 컴파일 산출물 경로가 바뀌면 `__dirname`, 상대 경로의 정적 파일·JSON·템플릿 로드, 동적 `require(변수)` 가 깨질 수 있다. 파일 시스템 경로를 쓰는 코드는 빌드 결과물에서도 실행해 확인하라.
- jest 목(mock)은 모듈 경로와 export 형태에 의존한다. `jest.mock` 대상의 export 형태가 바뀌면 목이 조용히 무력화될 수 있다. 테스트가 통과해도 목이 실제로 적용됐는지 확인하라.
</pitfalls>
