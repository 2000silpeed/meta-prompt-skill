## 단계별 진행

### Phase 0 — 조사 (코드 변경 없음)

### Phase 1 — 인프라 (아직 .js → .ts 변환 없음)
- `typescript`, `@types/node`, `@types/express`와 실제 사용 중인 라이브러리의
  `@types/*`를 devDependency로 추가하세요.
- `tsconfig.json`을 만드세요. 시작점은 `allowJs: true`, `checkJs: false`,
  `strict: false`입니다(이후 단계에서 올립니다). `outDir`, `rootDir`, `target`,
  `module`은 현재 Node 버전과 모듈 시스템에 맞추세요.
- jest가 .ts를 처리하도록 transform을 설정하세요(ts-jest, @swc/jest 등 중 프로젝트에
  맞는 것을 고르고 이유를 기록). 기존 .js 테스트가 그대로 돌아야 합니다.
- package.json에 `typecheck`, `build` 스크립트를 추가하세요.
- CI 워크플로에 typecheck 단계를 추가하세요.
- 빌드와 실행 방식: 개발 중에는 tsx/ts-node 같은 런타임 트랜스파일을 써도 되지만,
  운영은 `tsc`로 빌드한 JS를 실행하는 것을 기본으로 하세요. **`start` 스크립트,
  Dockerfile, 배포 설정을 바꾸는 변경은 별도 PR로 분리하고, PR 설명에 "배포 영향 있음"을
  명시하세요.** 운영 기동 방식이 바뀌는 지점이기 때문입니다.
- 이 단계가 끝나면 코드는 하나도 안 바뀌었는데 TS 툴체인이 동작하는 상태여야 합니다.

### Phase 2 — 파일 단위 전환 (allowJs 상태 유지)
- 정한 순서대로 .js → .ts로 바꾸고 타입을 붙이세요.
- `require`/`module.exports`를 `import`/`export`로 바꿀 때 기본 export와 named export의
  상호운용(`esModuleInterop`, `export =` 등) 때문에 런타임 동작이 바뀌지 않는지 특히
  조심하세요. 아직 JS로 남은 파일이 TS 파일을 require하는 경우를 꼭 확인하세요.
- `req.user`처럼 Express Request에 붙여 쓰는 커스텀 속성은 흩어진 단언 대신
  declaration merging(`types/express.d.ts` 등)으로 한 곳에서 정의하세요.
- 요청 body, query, 외부 API 응답, DB 결과처럼 외부에서 들어오는 데이터는 실제로
  검증된 것이 아니면 `unknown`이나 느슨한 타입으로 두세요. 검증 없이 정확한 타입을
  단언하면 거짓 안정감만 생깁니다. 런타임 검증(zod 등)을 추가하는 것은 동작 변경이므로
  이번 범위가 아닙니다. 필요해 보이면 기록만 하세요.
- 타입을 정하기 어려우면 `any`를 넓게 쓰지 말고, 이름 붙인 타입 별칭과
  `// TODO(ts-migration): ...` 주석을 남긴 뒤 MIGRATION.md에 기록하세요.

### Phase 3 — strict로 조이기
- 모든 앱 코드가 .ts가 되면 `allowJs`를 끄고, strict 계열 옵션을 하나씩 켜세요
  (`noImplicitAny` → `strictNullChecks` → 나머지). 옵션 하나에 커밋 하나 이상입니다.
- `strictNullChecks`로 드러나는 null/undefined 처리에서도 원칙 1이 적용됩니다.
  기존 동작이 "undefined면 터진다"였다면, 몰래 기본값을 넣어 고치지 말고 기록하세요.

### Phase 4 — 마무리
- 남은 `any`, `@ts-ignore`, TODO를 정리하고, 정리하지 못한 것은 사유와 함께 목록화하세요.
- 빌드 산출물로 서버를 실제 기동해서, 주요 엔드포인트 몇 개에 요청을 보내 기동과 응답을
  확인하세요(테스트가 덮지 않는 엔트리포인트와 설정 로딩을 검증하기 위해서입니다).
- 최종 요약을 작성하세요(아래 보고 형식 참고).

**설계 포인트와 조정할 만한 부분**

- **실행 전 결정할 것:** 운영 실행 방식을 tsc로 빌드한 JS로 할지, tsx 같은 런타임 트랜스파일로 할지는 팀 정책에 따라 다릅니다. 프롬프트는 tsc 빌드를 기본으로 두고, 배포에 영향을 주는 변경은 별도 PR로 분리해 확인받도록 했습니다. 이미 정한 방식이 있으면 그 문장만 바꾸면 됩니다.
- **"동작 불변"과 "테스트는 명세" 원칙에는 이유를 함께 적었습니다.** 장기 작업에서 가장 흔한 실패는 테스트 기대값을 바꿔 통과시키거나, 지나가다 버그를 고치면서 동작이 바뀌는 경우입니다. 이유를 알면 모델이 규칙에 없는 상황에서도 같은 방향으로 판단합니다.
- **MIGRATION.md 진행 기록:** 컨텍스트가 초기화돼도 이어서 작업할 수 있게 하는 장치이고, 사람이 진행 상황을 볼 때도 이 파일 하나만 보면 됩니다.
- **"멈추고 물어볼 것"에는 보류하고 계속 진행하라는 지시를 붙였습니다.** 비대화형으로 돌릴 때 질문 하나 때문에 전체 작업이 멈추지 않게 하기 위해서입니다.
- **완료 조건 6번(any 최소화)은 일부러 수치로 정하지 않았습니다.** "any 0개" 같은 숫자 목표를 주면 `unknown as X` 같은 우회로 숫자만 맞추는 경향이 있습니다. 대신 남은 것을 모두 목록화하게 해서 사람이 판단할 수 있게 했습니다.
- **분량이 부담되면** Phase 3(strict 전환)을 별도 작업으로 떼어 내도 됩니다. 1차 목표를 "전 파일 .ts 전환 + `noImplicitAny`까지"로 줄이면 한 번에 맡기기가 더 안정적입니다.
