```markdown
# 작업: 레거시 Express API 서버를 TypeScript로 점진 마이그레이션

## 배경
이 저장소는 JavaScript로 작성된 Express API 서버이고, 실제 운영 중입니다.
- 런타임: Node {{버전}}, 패키지 매니저: {{npm/yarn/pnpm}}, 모듈 방식: {{CommonJS/ESM}}
- 테스트: jest 약 120개. 지금 동작을 보장하는 근거는 사실상 이 테스트뿐입니다.
- CI: GitHub Actions (`.github/workflows/`)
- 운영 시작 명령: {{예: `node src/server.js`}}

목표는 서버 동작을 하나도 바꾸지 않고 코드베이스 전체를 TypeScript로 옮기는 것입니다.
한 번에 다 바꾸는 방식이 아니라, 매 단계가 끝날 때마다 테스트와 CI가 초록색이고
그 상태로 배포해도 되는 작은 단계들로 진행해 주세요. 작업이 길어서 컨텍스트가
여러 번 요약·초기화될 수 있습니다. 그래서 진행 상황은 머릿속이 아니라 저장소 안의 파일에 남겨야 합니다.

## 0단계: 조사와 계획 (코드 수정 전)
1. 디렉터리 구조, 진입점, 모듈 사이 의존 관계, 테스트 구성(jest 설정, 테스트 파일 위치),
   CI 워크플로, `package.json` 스크립트를 파악하세요.
2. `npm test`(또는 해당 명령)를 실행해서 기준선을 기록하세요. 통과/실패/스킵 수와,
   원래부터 실패하거나 불안정한 테스트 목록을 남깁니다. 원래 실패하던 테스트는 고치지 말고 기록만 하세요.
3. 저장소 루트에 `MIGRATION.md`를 만들어 다음을 적으세요.
   - 기준선 테스트 결과
   - 변환 순서. 의존성이 적은 쪽(utils, 상수, 설정)부터 시작해 models/services,
     middleware, routes/controllers 순으로 가고, app/server 진입점을 마지막에 둡니다.
   - 파일별 체크리스트 (`[ ]` 미착수 / `[~]` 진행 중 / `[x]` 완료)
   - 결정 사항 로그와 사람 확인이 필요한 질문 목록
   이 파일이 작업의 단일 진실 공급원(single source of truth)입니다. 컨텍스트가 초기화된 뒤에는
   먼저 `MIGRATION.md`와 `git log --oneline -20`을 읽고 이어서 진행하세요.

## 1단계: TypeScript 도입 (동작 변경 없음)
- `typescript`, `@types/node`, `@types/express`, 사용 중인 라이브러리의 `@types/*`, 그리고
  jest용 TS 변환기(`ts-jest` 또는 이미 babel을 쓰고 있다면 그 설정 확장)를 추가합니다.
- `tsconfig.json`은 `allowJs: true`, `checkJs: false`로 시작해서 JS와 TS가 같이 돌게 합니다.
  `strict`는 처음엔 끄고, 변환이 끝난 뒤에 옵션을 하나씩 켜 갑니다.
- CI에 `tsc --noEmit` 타입체크 단계를 추가합니다. 기존 단계(테스트, 린트 등)는
  지우거나 약하게 만들지 마세요.
- 이 단계가 끝났을 때 기존 테스트 결과는 기준선과 같아야 합니다.

## 2단계: 파일 단위 변환 반복
`MIGRATION.md` 순서대로 한 번에 1~5개 파일씩 진행합니다.
1. `git mv`로 `.js`를 `.ts`로 바꿔서 히스토리를 보존합니다.
2. 타입을 붙입니다. 함수 시그니처, 요청/응답 바디, DB 모델, 설정 객체를 우선합니다.
3. `tsc --noEmit`, jest 전체, 린트를 실행합니다.
4. 모두 통과하면 커밋하고 `MIGRATION.md` 체크리스트를 갱신합니다.
   커밋 하나에는 한 묶음만 담고, 메시지는 `ts-migrate: <대상>` 형식으로 씁니다.

### 동작 보존 규칙 (가장 중요)
- 이번 작업은 타입 추가와 문법 변환만 합니다. 리팩터링, 로직 개선, 의존성 메이저 업그레이드는
  하지 마세요. 그러다 버그를 발견하면 고치지 말고 `MIGRATION.md`의 "발견한 문제" 항목에 적으세요.
  타입이 붙으면서 잠재 버그가 드러나는 경우가 많은데, 그걸 고치면 동작이 바뀝니다.
- 다음 지점은 런타임 의미가 쉽게 바뀌니 특히 조심하세요.
  `module.exports`와 `export default`의 interop, `require`를 `import`로 바꿀 때
  달라지는 로딩 순서와 side effect, 런타임에 `module.exports`를 수정하는 코드, 동적 `require`,
  `this` 바인딩, `JSON` 파일 import, `__dirname` 사용.
- `req.user` 같은 Express 확장 속성은 `types/express.d.ts`에서 declaration merging으로 정의하고,
  각 파일에서 `as any`로 우회하지 마세요.
- 테스트의 assertion은 바꾸지 마세요. 테스트를 TS로 옮기는 건 해당 소스 변환이 끝난 다음에
  별도 커밋으로 합니다. 테스트 코드를 고쳐야만 통과하는 경우(예: import 경로)에는 커밋
  메시지와 `MIGRATION.md`에 이유를 적으세요. 테스트를 skip하거나 삭제해서 통과시키는 건 금지입니다.

### `any` 정책
- 당장 정확한 타입을 알 수 없으면 `any` 대신 `unknown`과 좁히기(narrowing)를 먼저 고려하세요.
- 그래도 필요하면 `// TODO(ts-migration): <이유>` 주석을 붙여서 `any`를 씁니다.
  `@ts-ignore`보다는 `@ts-expect-error`를 쓰세요.
- 이런 우회의 개수를 `MIGRATION.md`에 추적해서 줄어드는지 보이게 합니다.

## 3단계: 빌드와 실행 경로 전환
- 모든 소스가 `.ts`로 바뀌면 `tsc` 빌드(`dist/`)와 새 시작 스크립트를 준비합니다.
- 운영 시작 명령, Dockerfile, 배포 워크플로를 바꾸면 배포에 직접 영향을 줍니다. 그래서 변경안을 준비하되
  별도 PR로 분리하고, PR 설명에 "사람 검토 필요"라고 명시하세요. 직접 머지하지 마세요.
- 빌드 결과물로 서버를 실제로 띄워서 헬스체크나 주요 엔드포인트 몇 개에 응답하는지 확인하고, 결과를 기록하세요.

## 4단계: strict 강화
`noImplicitAny`, `strictNullChecks` 등 strict 옵션을 하나씩 켜고, 옵션마다 따로 커밋합니다.
여기서도 동작 변경은 없어야 합니다. null 처리 로직을 "고치고" 싶어질 때가 바로 그 경우입니다.
```
