```markdown
# 작업: 레거시 Express API 서버를 TypeScript로 점진 마이그레이션

## 배경과 목표
이 저장소({{저장소 이름/경로}})는 JavaScript로 작성된 Express API 서버이며 운영 중입니다.
점진적으로 TypeScript로 옮기는 장기 작업을 맡깁니다.

최종 목표:
- `src/`(또는 실제 소스 디렉터리)의 모든 `.js` 파일을 `.ts`로 전환
- `tsc --noEmit`이 `strict: true`에서 통과
- 기존 jest 테스트(약 120개)가 모두 통과하고 CI(GitHub Actions)에서 타입 체크가 돌아감

이 작업에서 가장 중요한 것은 **런타임 동작을 바꾸지 않는 것**입니다. 운영 중인 서버라서
"타입은 깔끔해졌는데 응답 형태나 에러 처리가 미묘하게 달라지는" 결과는 실패로 봅니다.
타입을 붙이다 기존 버그를 발견해도 이 작업 안에서 고치지 말고 기록만 해 주세요.
버그 수정은 별도로 판단하겠습니다.

## 지켜야 할 제약
- **테스트가 계약입니다.** 테스트를 삭제하거나 `.skip` 처리하거나 assertion을 약하게 바꿔서
  통과시키지 마세요. 테스트 파일도 TS로 옮겨도 되지만 검증 내용은 그대로 두어야 합니다.
  테스트가 깨지면 원인을 소스 쪽에서 찾으세요. 테스트 자체가 잘못됐다고 판단되면
  고치지 말고 `MIGRATION.md`의 "확인 필요" 항목에 남기세요.
- **모든 커밋 시점에 `npm test`와 타입 체크가 통과해야 합니다.** 중간에 깨진 상태로
  다음 파일로 넘어가지 마세요. 그래야 어느 커밋에서 멈춰도 배포 가능한 상태가 유지됩니다.
- 한 커밋에는 1~5개 정도의 관련 파일만 전환하세요. 리뷰할 수 있는 크기를 유지하기 위해서입니다.
- 의존성은 TS 도입에 필요한 것(`typescript`, `@types/*`, jest TS 변환기 등)만 추가하세요.
  기존 런타임 의존성의 메이저 버전 업그레이드는 하지 마세요.
- `any`, `as any`, `@ts-ignore`, `@ts-expect-error`는 최후의 수단입니다. 꼭 써야 하면
  `// TODO(ts-migration): 이유`를 함께 달고 개수를 `MIGRATION.md`에 기록하세요.
  외부 입력(req.body, req.query, 환경 변수 등)에는 `any`보다 `unknown`과 좁히기를 우선하세요.
- 리팩터링, 이름 변경, 로직 정리, 포매팅 일괄 변경은 이 작업의 범위가 아닙니다.
  diff가 "타입 추가와 확장자 변경"으로 읽혀야 합니다.

## 진행 방식

### 0단계: 조사와 기준선 확보 (코드 변경 없음)
1. 저장소 구조, `package.json`, 진입점, 모듈 시스템(CommonJS/ESM), Node 버전,
   jest 설정, `.github/workflows/*`, 배포/실행 스크립트(Dockerfile, Procfile 등)를 읽으세요.
2. `npm test`를 실행해 기준선을 기록하세요(통과/실패 개수, 실행 시간).
   **이미 실패하는 테스트가 있으면** 그 목록을 기록하고, 그 테스트는 마이그레이션 전후로
   같은 상태인지만 확인하세요.
3. 파일 간 import 그래프를 대략 파악해 의존성이 없는 leaf 모듈(유틸, 상수, 순수 함수)부터
   라우터/앱 진입점 순으로 전환 순서를 정하세요.
4. 위 내용을 저장소 루트의 `MIGRATION.md`에 정리하세요(형식은 아래 참고).

### 1단계: 인프라 (JS와 TS 공존)
- `tsconfig.json`: `allowJs: true`로 시작하고, 처음에는 `strict: false`로 두되
  `noImplicitAny`처럼 켤 수 있는 옵션은 가능한 범위에서 켜세요. 기존 모듈 시스템과
  출력 형식을 바꾸지 마세요(CommonJS면 CommonJS 유지).
- jest가 `.ts`를 실행할 수 있게 설정하세요(ts-jest, @swc/jest, babel 중 하나를 선택하고,
  왜 그걸 골랐는지 `MIGRATION.md`에 한 줄로 남기세요).
- `package.json`에 `typecheck` 스크립트(`tsc --noEmit`)를 추가하세요.
- GitHub Actions 워크플로에 기존 테스트 단계와 별도로 타입 체크 단계를 추가하세요.
  기존 job, 시크릿, 배포 단계는 건드리지 마세요.
- **운영 실행 방식 변경**(`node src/index.js` → 빌드 산출물 실행 등)은 이 단계에서 하지 마세요.
  `allowJs` 상태에서 JS 진입점이 그대로 동작하게 두고, 빌드/실행 방식 전환안은
  `MIGRATION.md`에 제안으로만 적으세요.

### 2단계: 파일 단위 전환 (대부분의 시간이 여기 들어갑니다)
각 단위마다 다음을 반복하세요:
1. 대상 파일을 `git mv`로 `.ts`로 바꾸세요(히스토리 보존).
2. 타입을 추가하세요. 공용 도메인 타입은 `src/types/`에 모으고,
   Express의 `Request`/`Response` 확장(예: `req.user`)은 declaration merging으로 한 곳에서 처리하세요.
3. `npm run typecheck && npm test`가 통과하는지 확인하세요.
4. 커밋하고 `MIGRATION.md`의 진행 상황을 갱신하세요.

막히는 파일(동적 프로퍼티 접근이 많거나 타입 정의가 없는 라이브러리 등)은 30분 이상
붙잡지 말고 `MIGRATION.md`에 이유와 함께 "보류"로 기록한 뒤 다음 파일로 넘어가세요.

### 3단계: strict 단계적 적용
모든 파일이 `.ts`가 되면 `strict` 관련 옵션을 하나씩 켜세요
(`strictNullChecks` → `strictFunctionTypes` → … → `strict: true`).
옵션 하나마다 커밋하고, 에러가 많으면 디렉터리 단위로 나눠 처리하세요.
null 체크를 추가하면서 동작이 바뀌는 경우(예: 이전에는 undefined가 그대로 응답에 실리던 경우)는
동작을 보존하는 쪽으로 작성하고 기록하세요.

### 4단계: 정리
`allowJs` 제거, 남은 `TODO(ts-migration)` 목록 정리, 최종 보고서 작성.
```

**작성 의도와 조정할 만한 부분**

- **가장 중요한 두 가지는 "테스트가 계약" 원칙과 `MIGRATION.md`를 통한 상태 관리**입니다. 장기 작업에서 흔한 실패는 두 가지예요. 하나는 테스트를 약하게 바꿔서 초록불을 만드는 것이고, 다른 하나는 컨텍스트가 요약된 뒤 무엇을 했는지 잃어버리는 것입니다. 두 원칙이 각각을 막습니다.
