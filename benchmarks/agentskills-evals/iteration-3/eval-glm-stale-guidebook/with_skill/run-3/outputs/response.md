# 목표
결제 모듈에서 금액의 소수점 반올림이 "가끔" 틀리는 버그를 찾아 원인을 고친다.
증상만 가리는 패치가 아니라 근본 원인을 고치고, 같은 유형의 버그가 다시 생기지 않도록 회귀 테스트를 남긴다.

# 이런 원인을 먼저 의심하라
- 금액을 float/double/JS number로 계산하는 경우. 예: 1.005 * 100 = 100.49999…, 2.675 → 2.67
- float를 decimal로 바꿀 때 정밀도를 잃는 경우. Decimal(1.005)는 이미 오차가 있으므로 Decimal("1.005")처럼 문자열이나 정수로 만들어야 한다
- 언어 기본 반올림이 의도와 다른 경우. Python round()와 BigDecimal HALF_EVEN은 은행가 반올림이고, JS toFixed()와 Math.round()는 음수나 .5에서 예상과 다르게 동작한다
- 계산 중간 단계마다 반올림해서 오차가 쌓이는 경우, 또는 반대로 반올림해야 할 단계에서 하지 않는 경우
- 음수 금액(환불, 할인)의 반올림 방향
- 통화별 소수 자릿수 차이(KRW·JPY 0자리, USD 2자리, KWD 3자리)
- 분할·안분 후 항목 합이 총액과 맞지 않는 경우(예: 100을 3으로 나누기). 이때는 나머지를 어느 항목에 배분하는지 규칙이 필요하다
- 직렬화나 DB 컬럼 타입(FLOAT, JSON number)에서 값이 바뀌는 경우

100÷3 안분, 퍼센트 할인 후 세금 계산, 위 값을 각 통화 자릿수에 대입한 경우

- 다음은 직접 하지 말고 근거와 함께 보고만 한다:
  · 기존 테스트의 기대값 수정. 기대값 자체가 틀렸다고 판단되면 그 근거를 보고한다
  · DB 스키마나 마이그레이션 변경(예: FLOAT를 DECIMAL로 바꾸기)
  · 외부 PG·API로 보내는 요청 형식이나 금액 단위 변경
  · 반올림 정책 결정(HALF_UP인지 HALF_EVEN인지, 안분 나머지를 어디에 배분할지). 이 부분은 기존 코드, 문서, PG 사양에서 근거를 찾고, 근거가 없거나 서로 충돌하면 임의로 정하지 말고 선택지를 보고한다
  · git commit/push, 의존성 추가
- 이미 저장된 금액 데이터를 보정하는 일은 하지 않는다. 영향 범위만 추정해서 보고한다.
