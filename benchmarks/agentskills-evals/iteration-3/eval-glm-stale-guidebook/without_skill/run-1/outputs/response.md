# 작업: 결제 모듈의 금액 반올림 버그 수정

## 배경
결제 모듈에서 금액의 소수점 반올림 결과가 가끔 틀린다. 매번이 아니라 특정 금액에서만 1원(또는 최소 통화 단위 1) 정도 차이가 난다.

- 저장소 / 모듈 위치: [예: src/payment/, services/billing/]
- 언어·프레임워크: [예: TypeScript + NestJS / Java Spring / Python Django]
- 알려진 재현 사례: [예: 상품 19,900원, 할인 15%, 부가세 10% → 기대 X원, 실제 Y원]
  (사례가 없으면 비워 둔다. 아래 1단계에서 직접 찾을 것)
- 회사 반올림 정책: [예: 원 단위 사사오입(HALF_UP) / 은행가 반올림(HALF_EVEN) / 버림. 모르면 "미정"]

## 진행 순서 (반드시 이 순서로)

### 1단계: 조사 (아직 코드 수정 금지)
결제 금액이 계산·변환·저장·표시되는 경로를 전부 찾아서 목록으로 만든다.
특히 아래 패턴을 grep으로 찾아 하나씩 확인한다.
- 금액에 부동소수점(float/double/JS number)을 쓰는 곳
- toFixed, Math.round, round(), parseFloat, Number(), floor, ceil
- BigDecimal인데 new BigDecimal(double)로 만들거나, setScale/divide에 RoundingMode가 없는 곳
- Python에서 Decimal(float)로 만들거나 기본 round()(은행가 반올림)를 쓰는 곳
- 반올림을 여러 번 하는 곳(중간 단계 반올림 → 누적 오차)
- 항목마다 반올림한 합과 합계를 반올림한 값이 다를 수 있는 곳(할인·세금·분할결제·환불 배분)
- 통화마다 소수 자릿수가 다른데 2자리로 고정된 곳(KRW·JPY는 0자리, USD는 2자리 등)
- DB 컬럼 타입(FLOAT/DOUBLE인지 DECIMAL/정수 최소단위인지), 직렬화/역직렬화 시 변환
- 외부 PG사 API에 넘기는 금액 포맷

### 2단계: 재현 테스트 작성
- 버그를 재현하는 실패 테스트를 먼저 작성하고 실제로 실패하는지 실행해서 확인한다.
- 경계값을 포함한다: x.5 정확히 반인 값, 0.1+0.2 계열, 1.005, 2.675, 큰 금액,
  음수(환불), 0원, 여러 품목 합산, 퍼센트 할인 + 세금 조합, 분할 결제.
- 재현 사례를 찾지 못했다면 위 경계값으로 속성 기반/대량 비교 테스트를 돌려
  어떤 입력에서 틀리는지 찾는다.

### 3단계: 원인 확정
코드를 고치기 전에 근본 원인을 "어느 파일 몇 번째 줄에서, 어떤 입력이, 왜 틀리는지"로 설명할 수 있어야 한다.
원인이 둘 이상이면 모두 적는다.

### 4단계: 수정
- 원칙: 금액은 정수 최소 단위(예: 원, 센트) 또는 10진 Decimal 타입으로만 다룬다.
  부동소수점은 쓰지 않는다.
- 반올림은 정책에 맞는 모드를 명시해서 한 곳(공용 유틸 함수)에서만 하고,
  계산 마지막 단계에서 한 번만 한다.
- 배분(할인·세금을 품목별로 나누기 등)은 나머지를 마지막 항목에 몰아주는 등
  합계가 정확히 맞도록 처리한다.
- 변경 범위는 버그 수정에 필요한 만큼으로 제한한다. 관계없는 리팩터링은 하지 않는다.
- 반올림 정책 자체를 바꿔야 할 것 같거나(예: HALF_EVEN → HALF_UP), DB 스키마나 마이그레이션,
  외부 API 계약을 바꿔야 한다면 수정하지 말고 보고서에 제안으로만 남긴다.
  기존 거래 데이터와 정산 금액이 달라질 수 있다.

### 5단계: 검증
- 2단계의 실패 테스트가 통과하는지 확인한다.
- 결제 관련 기존 테스트 전체와 가능하면 전체 테스트 스위트를 돌려서 회귀가 없는지 확인한다.
- 테스트를 통과시키려고 기존 테스트의 기대값을 바꾸지 않는다. 기대값 자체가 틀렸다고 판단되면
  바꾸기 전에 근거를 보고서에 적는다.

## 금지 사항
- git commit/push, 배포, 실제 PG 연동 호출, 운영 DB 접근 금지
- 테스트 스킵·삭제로 통과시키기 금지
- 확인하지 않은 내용을 "고쳤다"고 보고하기 금지

## 최종 보고 형식
1. 근본 원인 (파일:줄, 원인이 되는 입력 예시, 기대값 vs 실제값)
2. 수정 내용 (변경 파일 목록과 각 변경 이유)
3. 추가한 테스트 목록
4. 테스트 실행 결과 (실행한 명령어와 통과/실패 수 그대로)
5. 수정하지 않았지만 같은 유형의 위험이 남아 있는 곳
6. 사람이 결정해야 할 사항 (반올림 정책, 스키마 변경, 기존 데이터 영향 등)
