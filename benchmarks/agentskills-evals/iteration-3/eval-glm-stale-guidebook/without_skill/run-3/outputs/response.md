```markdown
# 작업: 결제 모듈의 금액 소수점 반올림 오류 수정

## 배경
결제 모듈에서 가끔 금액의 소수점 반올림 결과가 틀린다. 항상 틀리지는 않고 특정 금액이나 조건에서만 틀린다.

- 결제 모듈 위치: [예: src/payment/, services/billing/ — 모르면 직접 찾을 것]
- 언어/프레임워크: [예: TypeScript/Node, Java/Spring, Python]
- 실제로 틀린 사례(있으면 적기):
  - 입력: [예: 단가 19.99 × 수량 3, 할인 15%] → 기대값: [예: 50.97] / 실제값: [예: 50.96]
- 반올림 정책: [예: 통화 최소 단위까지 HALF_UP / 모르면 "기존 코드와 테스트에서 추론"]
- 다루는 통화: [예: KRW(소수 0자리), USD(2자리)]

## 진행 순서 (순서대로 할 것)

1. **조사 (코드 수정 금지)**
   - 결제 모듈에서 금액을 계산·변환·반올림·포맷하는 코드를 모두 찾는다.
   - 아래 의심 지점을 하나씩 확인하고, 해당하는 곳을 `파일:라인` 형식으로 적는다.
     - 금액에 float/double 같은 이진 부동소수점을 쓰는 곳 (예: `0.1 + 0.2`, `price * 1.1`)
     - 반올림 방식이 섞여 있는 곳 (HALF_UP / HALF_EVEN(은행가 반올림) / 버림 / 언어 기본 `round()`의 동작 차이)
       - 예: Python `round(2.675, 2)`는 2.67, JS `toFixed`도 부동소수점 오차를 그대로 반영함
     - 계산 중간 단계마다 반올림해서 오차가 누적되는 곳 (항목마다 반올림한 뒤 합산 vs 합산한 뒤 반올림)
     - 할인, 세금, 수수료, 분할결제, 환불을 비율로 나눈 뒤 합계가 원금과 1단위 어긋나는 곳
     - 통화별 소수 자릿수를 하드코딩한 곳 (KRW·JPY는 0자리인데 2자리로 처리하는 등)
     - 문자열과 숫자 사이 변환, DB 컬럼 타입(FLOAT vs DECIMAL), 직렬화(JSON number) 과정에서 정밀도가 깎이는 곳

2. **재현 테스트 먼저 작성**
   - 위 사례와 조사에서 찾은 의심 지점을 실패하는 단위 테스트로 만든다.
   - 경계값을 반드시 포함한다: x.xx5, 음수(환불), 0, 아주 큰 금액, 1원/1센트, 3등분처럼 나누어떨어지지 않는 분할.
   - 수정 전에 테스트가 **실제로 실패하는지** 실행해서 확인하고, 그 출력을 기록한다.

3. **근본 원인 수정**
   - 금액은 언어의 정확한 십진 타입(Decimal / BigDecimal / decimal.js 등, 이미 프로젝트에 있는 것 우선)을 쓰거나 최소 단위 정수(원, 센트)로 다룬다.
   - 반올림은 한 곳(공통 함수)으로 모으고, 정해진 정책대로 **최종 단계에서 한 번만** 한다.
   - 분할·배분 계산은 나머지를 마지막 항목(또는 정해진 규칙)에 몰아서 합계가 원금과 정확히 같게 만든다.
   - 증상만 가리는 땜질(결과에 +0.0001 더하기, 특정 값 예외 처리 등)은 금지한다.

4. **검증**
   - 새 테스트와 기존 테스트 전체를 실행해서 모두 통과하는지 확인한다.
   - 기존 테스트의 기대값을 바꿔야 한다면 임의로 바꾸지 말고, 왜 바꾸는지 보고서에 적는다.

## 제약
- 결제 모듈과 직접 관련된 파일만 수정한다. 관련 없는 리팩터링, 포맷 변경, 의존성 업그레이드는 하지 않는다.
- 공개 API 시그니처, DB 스키마, 외부 PG사 연동 요청 형식은 바꾸지 않는다. 바꿔야 한다면 **수정하지 말고 멈춘 뒤 이유를 보고**한다.
- 반올림 정책을 코드와 테스트에서 확정할 수 없거나 곳마다 다르게 쓰이고 있으면, 임의로 하나를 고르지 않는다. 선택지와 각각의 영향을 정리해서 보고하고 멈춘다.
- 새 라이브러리 추가가 필요하면 먼저 보고한다.

## 최종 보고 형식
1. 근본 원인: 어느 `파일:라인`에서 왜 틀렸는지, 틀린 값이 나오는 구체적 입력 예시
2. 수정 내용: 변경한 파일 목록과 각각의 변경 요약
3. 테스트: 추가한 테스트 목록, 수정 전 실패 출력과 수정 후 통과 출력
4. 영향 범위: 이번 수정으로 기존과 결과가 달라질 수 있는 케이스 (예: 과거 주문 재계산, 정산 금액)
5. 미해결 사항: 확인하지 못했거나 판단을 사람에게 넘긴 부분
```

- **실행 방식:** 에이전트가 한 번에 끝까지 진행하게 하려면 1~2단계만 먼저 돌려 원인 보고를 받으세요. 그 내용을 확인한 뒤 3~4단계를 이어서 시키는 방식이 결제 코드에서는 더 안전합니다.
