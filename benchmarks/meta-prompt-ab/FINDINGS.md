# 모델별 메타 프롬프트 A/B 관측

총 12회 실행을 완료했다. 이번 상세 명세 기반 코드 수정 과제에서는 Luna의 요구사항 누락이
메타 조건에서 줄었다. Astra와 Sol은 두 조건의 평가 점수가 같았다. 이 관측은 모델 전반의
품질 순위나 메타 프롬프트의 보편적 효과를 입증하지 않는다.

## 결과

각 숫자는 사전에 고정한 41개 테스트 중 통과 수다. 시간은 조건별 두 실행의 평균이다.

| 모델 | 일반 지시 1·2회 | 메타 프롬프트 1·2회 | 일반 평균 시간 | 메타 평균 시간 |
|---|---|---|---:|---:|
| Astra | 40, 40 | 40, 40 | 98.7초 | 137.1초 |
| Sol | 40, 40 | 40, 40 | 328.3초 | 245.3초 |
| Luna | 37, 39 | 40, 40 | 125.9초 | 130.5초 |

- Astra: 점수 차이 없이 메타 조건이 평균 38.3초 더 걸렸다. 두 반복 모두 같은 방향이다.
- Sol: 점수 차이 없이 메타 조건이 평균 83.0초 짧았다. 두 반복 모두 같은 방향이지만 메타 실행 자체가 304.6초와 186.0초로 크게 달랐다.
- Luna: 메타 조건은 두 반복에서 각각 3개·1개 항목을 더 통과했다. 평균 수행 시간은 4.5초 길었다.

모든 실행에서 공개 테스트와 저장된 자체 테스트가 통과했다. 이것만으로 계약 전체 충족을
판정할 수 없다는 점은 별도 평가 점수에서 확인된다. 개별 명령으로 수행한 임시 검증은
참가자의 handoff 기록이며, 부모가 재실행한 공개·자체 파일 테스트와 구분한다.

## 어떤 누락이 줄었나

Luna 일반 1회는 숫자 입력 검증, 환불 인자 검증, 예약 상태의 전체 취소 규칙을 놓쳤다.
일반 2회도 숫자 입력 검증에서 실패했다. 메타 조건은 두 번 모두 이 항목을 통과했다.
첫 일반 실행의 코드에는 bool을 허용하는 정수 판정과 자기 자신을 비교하는 예약 취소 조건이 있었다.
점수 차이는 문서 형식에 대한 주관적 채점이 아니라 계약 동작 테스트에서 발생했다.

12개 후보 모두 10**5000 크기의 금액이 포함된 주문 생명주기 검사를 실패했다.
이 사례는 앞 팀 구조 실험에서 발견됐으며 이번에는 첫 실행 전에 양쪽 조건의 평가에
동일하게 고정했다. 참가자에게 특정 결함의 힌트나 평가 피드백은 제공하지 않았다.
일반적인 목표·제약·검증 지시의 정리만으로 이 경계 사례까지 해결되지는 않았다.

## 메타 프롬프트 스킬을 어떻게 적용했나

기존 meta-prompt의 가이드북 카드를 읽고 일반 요청을 모델별 목표·맥락·제약·완료 기준·출력
형식으로 미리 변환했다. 최종 지시문은 각 실행의 prompt.txt에 저장하고 실행 전에 해시를 고정했다.
별도의 변환 에이전트를 후보마다 추가한 실험은 아니다.

Astra는 Codex 카드와 범용 폴백, Sol은 Codex와 GPT-5.6 Sol 카드, Luna는 Codex와 GPT-5 계열
공통 카드를 사용했다. Astra 전용 가이드와 Luna 전용 카드는 없다. 전용 최적화의 검증 수준이
동일하다고 표현하지 않는다. 적용 범위와 실행 순서는 [PROTOCOL.md](PROTOCOL.md)에 있다.

## 해석의 범위

두 조건 모두 상세한 CONTRACT.md와 동일한 실험 지시를 받았다. 따라서 이번 결과는 이미
명세가 갖춰진 상황에서 프롬프트를 추가로 구조화한 효과다. 모호한 요청에서 필요한 정보를
수집하는 스킬 전체의 효과나 팀 구성 효과를 측정한 것은 아니다.

한 합성 과제, 조건당 두 번뿐이다. 82개 테스트 판정의 합계를 82개의 독립 실험으로 취급하지
않는다. 평가 점수가 높아도 모든 결함이 없다는 뜻은 아니다. 가이드북에 특화된 형식, 추가
문구, 영어 항목명 등의 영향을 분리하는 ablation도 수행하지 않았다. 이 비교만으로 특정
카드의 효과나 프롬프트 길이의 효과를 따로 주장할 수 없다.

시간은 시작 마커부터 completion.json 저장까지다. 부모의 호출 준비·대기, 모델 처리,
도구 사용 등이 포함되고 순수 추론 속도는 분리하지 않았다. 특히 첫 Astra 메타 실행은
시작 마커 이후 부모 문맥 복원이 있었으며 이 준비 지연을 별도로 계측하지 않았다.
프롬프트 컴파일·평가·보고서 작성 시간은 제외했으므로 스킬 전체의 소요 시간도 아니다.
토큰 수와 실제 금액은 미측정이다. 모델명과 medium 설정은 네이티브 호출에 요청한 값이며
서비스 내부 모델 리비전이나 스케줄링은 별도로 계측하지 않았다.

실용적으로는 이 과제의 Luna에서 요구사항 누락 감소라는 개선 신호를 얻었다.
Astra·Sol의 정확성 향상은 관측하지 못했다. 이 한 과제의 결과를 팀 구성 스킬의 고정 모델
순위로 넣지 않고, 작업별 비교 기록으로 보존한다. 후속 실험에서는 서로 다른 과제와
명세의 상세도를 사전에 구분하고 반복 수를 늘려 재현 여부를 확인할 수 있다.

## 보존과 검증

12개 새 에이전트의 산출물, 요청 모델·추론 설정, 지시문, 시작·완료 기록, 코드 해시,
평가 결과와 테스트 로그를 보관했다. 부모가 후보 코드를 수정하지 않았다.
`audit.py`는 6개 조건 × 2회, 12개의 서로 다른 에이전트 기록, 반복 간 동일 지시문,
동결 입력·코드 해시·계약·공개 테스트 보존 및 완료 구간 비중첩을 확인했다.
이는 기록의 일관성 검사이며 에이전트의 모든 파일 접근을 보안 감사한 것은 아니다.
