# 원요청과 현재 meta-prompt 직접 비교 — 2026-10-28

**이번 상세 명세 과제에서는 메타 적용의 추가 성능 이득을 확인하지 못했다.**
텍스트와 코드 모두 두 조건이 동점이다. 스킬이나 기본 운용 기준은 변경하지 않는다.

## 실제 점수

| 범주 / 요청 모델 | 원요청 | 메타 적용 |
|---|---:|---:|
| 텍스트 / GPT-6 Luna | 12/12 | 12/12 |
| 텍스트 / GPT-6.1 Terra | 12/12 | 12/12 |
| 텍스트 합계 | **24/24 (100%)** | **24/24 (100%)** |
| 코드 비공개 검사 / GPT-6 Luna | 80/82 | 80/82 |
| 코드 비공개 검사 / GPT-6.1 Terra | 80/82 | 80/82 |
| 코드 검사 합계 | **160/164 (97.56%)** | **160/164 (97.56%)** |
| 코드 41개 전부 통과한 구현 | **0/4** | **0/4** |

관측된 통과율 차이는 두 범주 모두 **0%p**다. 텍스트 원자 값·구조도 양쪽 1,388/1,388이다.
두 범주의 점수와 검사 항목을 임의로 합산하지 않는다. 조건당 반복은 2회이고,
묶음 안 과제·검사 항목은 독립 표본이 아니므로 통계적 동등성이나 유의성을 주장하지 않는다.

## 양쪽에 남은 실패

코드 8개 모두 `test_41_unbounded_integer_event_lifecycle`에서 실패했다.
5천 자리 정수 이벤트의 중복 판정 fingerprint를 만드는 경로에서 Python의 정수 문자열
변환 제한(4,300자리)을 만났다. 메타 적용도 이 결함을 해결하지 못했다.
원래 fixture는 20/41이었고 수정 뒤 양쪽 모두 40/41이 됐다. 이 공통 개선을 메타 효과로 세지 않는다.

모든 구현의 CONTRACT.md와 원래 공개 테스트가 보존됐고 handoff/완료 기록도 존재한다.
공개 테스트 통과나 완료 보고가 있어도 비공개 41개를 모두 통과한 것은 아니다.
저장된 코드만 별도 임시 폴더에 복원해 독립 재실행했으며 8×41개 검사 ID·상태가
원래 채점 기록과 모두 일치했다.

## 무엇을 비교했나

- 직전 스트레스 실험의 6개 목표·업무 자료·출력 계약을 원요청으로 사용했다.
  공통 메타 문구만 제거했고, 원요청을 일부러 불리하게 만들지 않았다.
- 독립 변환기가 실제 SKILL.md, registry/index와 필요한 카드들을 읽고 타깃별 실행 틀을 만들었다.
  원문은 SOURCE 위치에 통째로 보존했다. 코드 계약은 양쪽에 동일한 파일로 제공했다.
- 변환기는 정답·비공개 검사·구현 코드·이전 모델 출력을 보지 않았다.
  실제 첫 변환본을 독립 검토한 뒤 고정했고, 좋은 결과가 나올 때까지 다시 만들지 않았다.
- Luna/Terra 요청 조건에서 raw/meta 각각 2회 새 context로 실행했다.
  텍스트 8개 묶음(48개 과제 결과), 코드 8개 구현이며 양쪽에 같은 도구·범위·설정을 줬다.
  용량 부족·입력 오류 등의 복구 호출은 이번에는 없었다.

## 추가 부담과 변환 결함

타깃별로 변환을 한 번씩 수행해 **변환 호출 2회가 추가**됐다. 생성된 틀은 두 반복에 재사용했다.

| 타깃 | 텍스트 6개 원문 합계 | 메타 지시 추가 | 코드 요청 문자 수 |
|---|---:|---:|---:|
| Luna | 39,518자 | +1,626자 (+4.1%) | 73 → 584자 |
| Terra | 39,518자 | +2,122자 (+5.4%) | 73 → 613자 |

코드 요청 문자 수에는 양쪽에 같은 작업 파일·계약 내용이 포함되지 않는다.
문자 수를 토큰·실제 과금으로 환산하지 않는다. 비용·지연 우열은 측정하지 않았다.

독립 검토에서 Luna ledger 틀의 추가 설명 유도 가능성, 코드 틀의 절차 확대,
두 코드 틀의 SOURCE 안에 계약 전문이 있다는 위치 오해를 발견했다. 그대로 보존해 평가했다.
공통 실행 안내는 양쪽 모두 실제 CONTRACT.md 파일을 읽도록 했으므로 위치 오해의 영향은
완화됐을 수 있다. 해당 표현은 실제 변환 품질의 한계다.

## 해석의 범위

원요청에 이미 상세 명세가 있어서 메타가 채울 빈틈이 적다. **명확한 요청에도 메타가 항상
더 낫다는 주장은 이번 결과로 뒷받침되지 않는다.** 모호한 요청의 정리, 모델별 제약 누락,
실제 창작 품질·이미지 생성·다른 도메인의 효과는 이번에 측정하지 않았다.

실험한 형태는 스킬이 생성한 실행 틀 + 불변 원문이다. 자유 재작성 전반이나 시스템 지침을
완전히 제거한 LLM 비교가 아니다. native agent의 공통 지침과 로컬 Python 도구는 양쪽에 있다.
실제 backend 모델·effort·토큰은 도구에서 관측되지 않아 unknown이며 표의 모델은 요청값이다.
각 타깃의 변환 1회만 사용했으므로 변환 자체의 변동성도 측정하지 않았다.
