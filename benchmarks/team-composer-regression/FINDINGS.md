# 다중 모듈 회귀 수정 실험에서 확인한 점

5개 모듈, 시작 코드 201줄의 주문·재고 엔진을 수정하는 실제 코딩 과제다. 시간대, 정수 할인·환불, 재고 원자성, TTL rollback, 중복 이벤트, replay 순서의 상호작용을 다뤘다. 공개 테스트 6개를 주고, 별도 에이전트가 공개 계약만으로 작성한 40개 테스트를 평가에 사용했다.

## 사전 고정 평가

수정 전 코드는 20/40이었다. 세 구성 각각 두 번의 실행 결과는 아래와 같다.

| 구성 | 평가 통과 합계 | 평균 시간 | 회당 호출 수 |
|---|---:|---:|---:|
| 단일 에이전트 | 80/80 | 79.7초 | 1 |
| 병렬 분담 + 통합 | 80/80 | 177.8초 | 3 |
| 제작 + 독립 검토 | 80/80 | 192.1초 | 2 |

전부 고정 평가를 통과했다. 이번 범위에서는 단독이 가장 빨랐다. 시간은 역할 생성·인계·검증을 포함한 실제 산출물 도달 시간이며 모델의 순수 연산 시간이나 금액은 아니다. 참여 에이전트 호출은 12회이며, 평가 테스트 제작 1회는 별도다.

## 고정 점수 밖에서 발견한 결함

첫 검토자(r1-review)와 두 번째 통합자(r2-parallel)가 서로의 결과를 보지 않고 같은 추가 결함을 찾아 수정했다. 원래 JSON fingerprint 구현은 Python 런타임의 정수 문자열 변환 제한 때문에 **5,001자리 정수를 금액으로 가진 유효한 이벤트**를 거부했다. 공개 계약에는 정수 크기 상한이 없다. 두 수정본은 큰 정수를 문자열로 바꾸지 않는 타입별 fingerprint로 해결했다.

이 발견 뒤 별도 재현 검사를 만들어 모든 최종본과 중간 산출물에 동일하게 적용했다. 아래는 사후 탐색 결과이며, 기존 40개 평가 점수에 합산하지 않았다.

| 실행 | 수정 전 단계의 추가 검사 | 최종본의 추가 검사 |
|---|---|---|
| r1-parallel | 실패 | 실패 |
| r1-review | 실패 | 통과 |
| r1-single | — | 실패 |
| r2-parallel | 실패 | 통과 |
| r2-review | 실패 | 실패 |
| r2-single | — | 실패 |

추가 검사는 검토자가 찾은 사례에서 선택했으므로 선택 편향이 있다. 이 한 경계값의 결과로 팀의 일반적인 품질 우위나 검토 성공률을 추정할 수 없다. 같은 검토·통합 구성을 사용해도 매번 이 오류를 찾지는 못했다.

평가 기준 구현도 이 추가 검사에서는 실패했다. 따라서 기준 구현의 40/40은 테스트의 실행 가능성과 기대값 대조를 위한 교정 결과이지, 계약 전체의 완전성을 증명한 결과가 아니다. 이 실험은 평가 테스트의 누락도 드러냈다.

## 스킬에 반영할 근거

- 이 범위의 수정은 단일 에이전트로 빠르게 처리할 수 있었다.
- 추가 검토·통합이 새로운 경계값 오류를 찾는 경우가 있었다. 고정 점수와 새 결함 발견을 따로 기록해야 한다.
- 이번 한 과제로 서비스별 순위나 팀 구성 임계값을 고정하지 않는다. 기존 최소 팀 원칙을 유지하며 오류 비용과 독립 검증의 필요성을 함께 고려한다.

각 구성 2회, 같은 합성 코드 과제의 탐색 결과다. 대규모 저장소·모호한 요구·서로 다른 모델·실제 비용은 평가하지 않았다. 정확한 가격과 토큰 사용량은 미측정이다.
