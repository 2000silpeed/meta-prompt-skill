# 서비스와 역할 배정

## 관측 기록

작업에 필요한 후보만 아래 정보를 기록한다. 전체 서비스 카탈로그를 매번 조사하지 않는다.

| 필드 | 의미 |
|---|---|
| service | 실행 환경·플랫폼 이름 |
| route | 현재 노출된 도구 이름, 확인한 CLI, 수동 전달 경로 |
| model | 실제 선택 가능한 모델 또는 `unknown` |
| capabilities | 이번 작업에 필요한 입력·출력·도구 능력 |
| availability | `ready`, `unverified`, `unavailable`, `manual-only` |
| evidence | 도구 스키마·읽기 전용 상태 확인 결과와 확인 시점 |
| cost | 확인한 단가·단위·출처 또는 `unknown` |
| constraints | 참조 파일, 출력 형식, 데이터 반출, 실행 시간 제약 |

`ready`는 현재 호출 경로가 확인됐다는 뜻이며 다음 호출의 성공을 보장하지 않는다. 인증 불확실성은 남겨 두고 실행 시 갱신한다. 추천 플러그인 목록은 설치·연결 증거가 아니다. 설치는 해당 호스트의 정책과 사용자 범위를 따른다.

## 선택 순서

1. 사용자 지정 서비스, 출력 형식, 데이터 경계, 예산 상한 등 필수 조건을 검사한다.
2. 자동 실행 후보는 필요한 능력과 호출 경로가 확인된 후보로 제한한다. 미확인 후보는 확인하거나 수동 전달 대안으로 둔다.
3. 결과물 적합성, 인계 손실, 병렬화 이익, 관측된 품질·비용·지연을 비교한다. 현재 가격·모델 기능이 필요하면 공식 출처 또는 런타임으로 확인한다.
4. 근거가 동률이거나 부족하면 현재 연결된 환경에서 적은 인계로 끝나는 구성을 선택한다. 숫자 점수나 가격을 만들어 순위를 정하지 않는다.
5. 권장안 하나와 선택 이유를 제시한다. 의미 있는 차이가 있을 때만 대안을 덧붙인다.

비용이 `unknown`인 외부 서비스는 “최저 비용”으로 선택할 수 없다. 비용 상한이 엄격하면 상한 준수를 확인할 수 없는 유료 후보의 실행을 보류한다. 품질 우선이어도 실제 수행 결과 없이 최고 품질이라고 단정하지 않는다.

## 작업 유형별 분해 예시

아래는 책임 분해의 출발점이다. 서비스의 성능 순위나 기본 팀 규모가 아니다.

| 결과물 | 가능한 역할 | 중요한 인계 |
|---|---|---|
| 소프트웨어 | 조사, 구현, 통합 검증 | 인터페이스·소유 파일·실행 가능한 검증 |
| 리서치 문서 | 근거 수집, 분석·작성 | 출처·발행일·사실과 추론 구분 |
| 브랜드 이미지·영상 | 콘셉트·대본, 자산 제작, 편집·검수 | 승인된 문구·참조 자산·길이·해상도 |
| 업무 자동화 | 흐름 설계, 연결·구현, 동작 확인 | 계정 범위·입출력·실패 처리 |
| 작은 프롬프트 작업 | 현재 에이전트 하나 | 최종 프롬프트·적용 카드 |

각 실행 서비스의 전문 스킬이 있으면 실제 작업 직전에 읽는다. 영상 제작의 필수 진입 스킬이나 Figma 도구의 선행 스킬을 팀 명세가 대체하지 않는다.

## 서비스·모델·가이드북 분리

- Codex에서 실행하는 서브에이전트는 실제 런타임 모델을 사용한다. Claude 역할이라는 이름을 붙인다고 Claude 서비스가 호출되는 것은 아니다.
- Claude·Gemini 등의 연결이 확인되면 그 경로와 모델을 기록하고 registry의 별칭으로 가이드북을 매칭한다.
- Higgsfield 같은 플랫폼에서는 사용 가능한 생성 모델을 확인한 후 해당 모델 가이드와 플랫폼 가이드를 선별한다.
- 호스트가 모델 상속만 지원하거나 모델 변경을 제한하면 그 조건을 지킨다. 서로 다른 역할에 같은 모델을 배정해도 정상적인 팀이다.
- 목록에 없는 새 서비스도 관측 기록을 채워 후보에 넣을 수 있다. 모델 가이드가 없으면 meta-prompt의 `_generic`으로 보충하고 한계를 표시한다.
